# Architecture

Your devices, and your team's, as one place for apps and agents. A network is one user's or one workplace's: its users, their devices, their apps, and a bucket (a folder or S3-compatible storage) holding everything, sealed. Every machine in it runs the same program; at its address, a few small Workers on Cloudflare, each named by its job, route, sign in, relay, carry pushes and sign bucket URLs. Two Workers are not like those: the remote MCP server is a client, and the Cloudflare node is a node. Each app's database for a scope is the truth, kept as signed steps in the bucket, and who can do what is the scope database's rows.

It's held to targets measured in `one-dev throwaway`, from a phone on mobile data where it matters: the web client usable within 1.5 s of a cold open; a remote MCP call adding at most 100 ms to a local one; a write seen on another device within 1 s; a call one round trip; no data rewritten when someone adds a device.

This page holds only what the code can't say. How each part works is its folder's doc: `cargo test map -- --nocapture` prints them all, as a map. `tests/contracts.rs` is where two languages must agree.

## Trust

- **Keys are opened only on clients**, the devices of users and their agents (apps, browsers, the CLI, the remote MCP server). **Nodes** run calls and hold no keys: a caller hands a node the database keys one call needs, which expire within the hour. The only exceptions are app schedules and the Vault, where a user or an admin chooses a machine to hold keys and can take them back, and a computer that is also its user's client device: its node opens that user's scopes with the device's own keys, for its CLI, its local MCP server and its schedules, and never opens anyone else's that way. So a hacked computer gives up its own user's data, as any of their devices would; for everyone else it's still only the calls it ran while it was hacked. The CLI and the local MCP server come with their computer's `oned` and are its node's own programs: they have no key or network of their own, and with no node running on a computer, they say what to install or start.
- **The Workers at the address open nothing.** A hacked node gets only the calls it ran while it was hacked; a hacked gateway, auth, relay, URL signer or push Worker reads no data. The Workers that serve browsers' code could take what browsers open, which is why they stay small, and why the Cloudflare account is guarded with a hardware security key. The remote MCP server is the same: its devices' secrets are sealed under their MCP clients' tokens, which reach it on every call, so whoever can change its code could open the keys of the scopes those devices were approved for. We consider it as secure as our Cloudflare account (Andre, 2026-11-05).
- **A native app's window shows only what the release key signed.** The web client it runs is the copy built into it or a bundle the release key signed (`src/web/bundle.rs`), which it checks before keeping it and again every time it starts: signature, shell version, and never older than what it has. The Workers and the bucket only carry bundles (at `<address>/updates/`), so a hacked Worker can't change what an app runs, where it could in a browser. The window loads the bundle from the app's own origin, never a remote one, so it can ask the app for exactly what the built-in copy can. A bad signature, a failed download or a bundle whose page doesn't start leaves the app on its last good bundle or the built-in one, which stays as the floor; a new one goes in when the window next opens, never under a running page.
- **An app's window runs the same client as a browser**, from its bundle (the client's Rust, as WebAssembly, in the page): a change to it, a `READS` bump included, reaches the app at its next open with no native build. Its device key stays in the OS's secret store, and signing and opening go through the app (the `Opens` and `Signs` traits' JS callbacks), which never hands the key over. An older Android System WebView has no Ed25519 in WebCrypto, so that page uses the shell's own client instead, as a shell built with no WebAssembly does. What runs with no window (widgets, notifications) stays the shell's Rust; a shell behind `READS` keeps showing the last widgets and the window says to update, and needs a native build, as a change to what the shell gives the page (`web::SHELL`) does.
- **Who can do what is signed, and kept in the bucket**: the scope database's steps, in the one order the bucket gives them, each checked by every reader. A change counts by who signed it, never by the time it claims.
- **Clients take who's who from the signed steps themselves**, from the freeze the network's recovery key signed, never from what a node or the relay says, and seal or hand keys only to whom they list.
- **Signing in only lets you ask.** It never opens a key, and never lets anyone in by itself. Someone already in the network says yes, at the time or in advance with an invite. A user has any number of linked identities, a passkey or an account at an OIDC provider the network has registered with (Google is one like any other), and one more is only ever linked from a device already signed in, which checks it and records it in the signed steps once its user taps to say so.
- **Who says yes.** A user's next device: one of their own, with the same short code on both screens. Someone not invited, at the network's domain, as the provider's signed token says: an admin, the same way, whose approval is the signed step listing them, so only admins add users; anyone else is refused at sign-in, before an admin is bothered. Someone invited by email: the invite, a signed step, is the approval, so they sign in with that email and go straight in. Someone sent an invite link: the link is the approval, its secret checked by the admin's device that made it, which lets them in with no tap unless their sign-in was finished from another link. Someone with no device left: an admin, once they've taken the lost ones out; what restores their own scope is a holder of the recovery key's, opening their own copy on their own device to seal it to the new one, by the code on its screen (`one devices restore`). A computer with no browser or no working sign-in: a QR, or a one-time link or code from a device already in, single use and short-lived. Every device of theirs then shows it joined, with Remove. Requests go out as ordinary pushes and stay until answered or expired.
- **Whoever answers checks the sign-in itself** (`src/onboarding/sign_in_proof.rs`), an OIDC provider's ID token for the network's own client or a passkey's assertion, each naming the new device and the network, so a hacked auth Worker can make requests and never approve one. A passkey's public key comes from auth, which keeps it, so it never counts as proof by itself. A user's next device whose sign-in can't show an ID token on record (a passkey, none it could check, or one not on record), and someone with no device left, are checked by the whole 16-letter code, as a short code alone can be matched by grinding keys offline. Auth reads a request's sign-in out only to an admin's device or that user's own. A "Not Me" is a step that takes the device's key out before it's ever listed, against that user only, and a browser refuses to seal anything to a key its own copy of who's who has taken out.
- **The recovery key's holders.** Whoever holds it can read everything and restore anyone, so an admin names them, in the network's settings, anyone in the network can see who they are, and everyone joining is told: "The owner of this network can see everything in it." Naming someone hands them nothing, and a network starts with no holder. Whoever has the key's file seals it on their own computer, once for each device, and a node keeps only what's sealed. It goes only to a holder's own device that is just a client and has said what it is: never a node, which holds no keys; a browser, whose code a Worker serves; a remote MCP client; or a passkey, which is wherever it syncs. A device's `platform` is only what it says of itself, and a hacked Worker can relabel a browser as a phone, and a hacked node can list a key of its own, so what really decides is its whole code, 16 characters of a hash of its key and seal key: whoever has the key's file computes it from the very key and seal key they're about to use, and seals only if it's what a person read from that device's own screen. Each copy is signed by the recovery key and counts only if that checks, so nothing anyone else put at its name can pose as it or block the real one. Taking someone off the list stops new seals to them, and can't take back what they already have: only replacing the recovery key does (`one devices recovery-key replace`), so that's how a holder's stolen device is undone. Whoever has the key's file names a new key; every epoch and Vault key the old one opens is sealed to the new one too, under its own name; each scope still in use gets a new epoch and Vault keys sealed to the new key and not the old, so what the old one opens stops growing; and copies held under the old key stop counting. Nothing already sealed is deleted. The recovery key signs those new epochs itself, as it must for a user with no device left: besides that it only lets a device of someone already in, each an entry in the log.
- **An invite is checked by every reader.** A newcomer's device can't write who's who itself, since it holds no key to `global`'s sealed steps, so an admin's device that's online writes it for them, with no tap: a `device` step carrying the provider's signed token and the key that signed it, fetched from the provider then and saved with the proof, as providers change their keys. Every reader checks it against the invite: only that user, for that email, that device, once. So it waits for an admin's device to be on, as shared data waits for a device holding its keys.
- **Link phishing** (Andre, 11-05): someone could start a sign-in on their own machine (any client they register, with a device of theirs named in it), send the user its link, and a provider pick or passkey tap would sign in their device. Auth tells by where a sign-in comes back to, which phishing can't change (a client's redirects can't be changed once it's registered, and only loopback or the app's own `<cli>://signed-in/` count as on the device): one finished from a link is marked, never goes straight in by an invite, and waits for a tap on a card naming the device and where it asked from. The short code doesn't cover this, as someone mid-phish has no second screen to compare it with. A tampered auth could mislabel one, and could get a user to sign in for its own device, as the browsers' code it serves could already take what a browser opens: that's the Cloudflare account's trust, and "joined · Remove" is what shows it.
- Whoever controls a user's provider account or passkey can sign in and ask. Their 2-step verification matters, and a network whose users are all at one domain has someone to say no. Letting a device in with none of the network's devices online, by a Worker that holds keys or a secret kept with the provider, was declined (Andre, 11-05): approval stays with clients.
- **One network, forever.** A key belongs to one network; networks never talk to each other.
- **Secrets stay put:** a Vault item's secret leaves a node only inside a request to one of its hosts, by an app switched on for it. Nothing reads one back.
- **Every client lists and may use the same tools.** What one may do is decided by its user's rules in the scope database and by what its keys open, never by which kind of client asks. A node signs a change to who can do what only as its own user's device, for its own programs; every other client signs its own.
- **Keys decide access; the relay decides who's on the network.** It admits only the network's endpoints, a list devices change by signed tells.
- **A push is sealed to the one device it's for.** The push Worker, and Apple's, Google's, Microsoft's and browsers' push services, carry locked bytes and read none of them: they see only that a device got a push, and when. A note says which of the network's devices sent it, and an action in one is checked by the device that gets it.
- **A service runs only the build its app's latest deploy names** for its platform, by hash, the deploy signed by whoever deployed it; or, for a built-in app's whose deploy names none, the newest release. The release key signs only what we ship (oned, the node, built-in apps' services), never a network's own code.
- **A device takes its own updates, by a signed record** at the network's address (`src/latest.rs`, `<address>/updates/newest`): a GET, nothing else of the network working, verified against the release key built in, never going backwards. A bad or missing record means staying on what it has and saying why, so no change can cut a device off from its own update. `one update` does the same by hand (`src/update`), with no background program running: it needs the record, and the network's address, which the node keeps in its home for it.
- **A service's program runs in its sandbox** (`src/services/sandbox.rs`): no keys, the network only to the hosts its app declares, and, unless its app declares it runs as the user (said wherever it's switched on), its own OS user and folder and none of theirs; so the sandbox protects a node, not who wrote the code. A machine that can't give one runs it without, and says so on it.
- **Only the URL signer holds the bucket's credentials;** everything in the bucket is sealed, so what it hands out opens nothing.

## The three rules

Who can do what is the signed steps of each scope's database, in the one order the bucket gives them, and every reader checks each step by three rules:

1. the network's first step, and the recovery key it names;
2. epochs never go down;
3. each step's signer holds the permission its change needs (`src/permissions/`).

A removed device's later steps fail rule 3, because they come after its removal in the one order.

## Designed, not built

- **`onet` and `oned`** (Andre, 11-10, being built). "Node" blurred several jobs, so it goes. **`onet`** is the entry point into the network, the same on every device: its identity, who's who, connecting to the best machine, opening keys, answering the API, and the store of what it last read. It's built into the phone app, runs in a browser's shared worker, in a Cloudflare Worker for each outside program (Claude.ai, ChatGPT), and in the background on a computer, where the desktop app, the CLI and the local MCP server are views on it with no keys of their own: one key per device. A phone is only ever a client, never an app server. **`oned`** only manages services, starting and stopping them and saying their versions, on computers and Cloudflare, as a user of `onet` like any other. **The app runtime is a service**, switched on per device, and does what needs something that stays on: answering other devices' calls, schedules, running apps' code, and the database copies that takes. Built so far: the API's document (`/api/openapi.json`) is made by `onet` for its own client, from the apps a node lists and what routes say of themselves (`src/says.rs`, a table that builds without the node), the same code in a browser, a computer and the Cloudflare node.
- **Nothing updates by itself** (Andre, 11-10, being built). Publishing a version makes it available. Devices tell the network what they're on, and every client shows each device's version with Update and Update All, pressed by a person or an agent; there's no automatic switch. `one update` is built, and restarts `oned` on the new build; a person or an agent presses Update from any client (Settings › Devices, Update All going one at a time, or `devices_update`), a signed ask carried blind by the relay, whose receiver checks who signed it and that they may remove this device, then starts `one update` and does nothing else. The body of `POST /relay/computes` and the signed ask are frozen with the signed record in `tests/contracts.rs`. Devices still take updates by themselves too, until that's been seen working, when the pull loop goes. Pre-production there's no compatibility code: a device left behind breaks until it's updated, and says so on itself. Only the signed record and the way of updating stay stable across versions.
- A user key, so a new device needs one handover and not a seal per scope: it's random, its secret sealed to each of its user's devices, and each scope's keys sealed to it beside today's seals. Nothing can hold one yet without widening what it could lose: a browser's code comes from a Worker; a native app's window gets only what its shell hands it; a computer's CLI opens keys as its node; a remote MCP client and an app schedules machine hold only what they were approved for. It waits for a native shell that keeps one itself.
- One key per scope at a time, changed only when a user or a lost device is removed, every database copied under the new key and the old one dropped. Today a scope has numbered epochs, and a new one is made when someone loses the right to open it.
- APNs, FCM and WNS for "wants in" on a real phone, waiting on the Apple, Firebase and Entra accounts.
- Services each running as their own OS user per scope, and Shell and Computer Use only with a grant for that device and session, approved by the user.
- What's left of the storage move: `docs/plan-storage-and-permissions.md`.
- Native apps keeping their own sealed copy, for reads with no network; writes while offline, replayed like a rebase, never repeating what went outside.

## Decided

Andre, 2026-11-05: the dumbest choice that works.

- A service's identity is its own OS user on Linux (systemd's `DynamicUser=`), Seatbelt as the user on a Mac. A Windows computer runs the app runtime and no services: AppContainer can't reach its device over loopback without an exemption only an administrator can make, so its sandbox is still to design, and none is published for it.
- On Windows, `oned` is a task of its user's, started at sign-in and looked at every minute, with no administrator (`install.ps1`): it stops at sign-out, like a Mac's launch agent, because a standard user can't have a task that runs signed out. A running program can be renamed but not overwritten, so an update gives the old file one more name, then renames the new one over each of its names (`os::replace_program`).
- A service that needs the user (`user: true`: Shell, AGENTS.md, AI Usage, the Mac's Apple-data services) is allowed for any app, said plainly when adding ("Runs as you on mac"), never silently.
- The machine that deploys builds a network's own app's service, for every platform it can build; nodes never build. A network's own Mac service gets no Mac permissions.
- One node runs a service. When it's gone nothing moves by itself: the app shows one problem box with Move. For a group's or everyone's app, the admin adding it picks one of their own nodes or the Cloudflare node, and any admin may move it to one of theirs.
- No Cloudflare Containers. The Cloudflare node runs the app runtime and services built for Cloudflare (Models answers with Workers AI there); Agent Devices stays on computers. Left: a network's own app's service built for Cloudflare, until someone needs one; a call a machine's node runs doesn't reach Workers AI; AI Usage doesn't show its spend.
- Risks: TCC attribution on a Mac is only learned by trying; `sandbox-exec` is deprecated though Apple ships on it (the fallback is an App Sandbox entitlement per helper, which only we can sign); moving a service loses its state unless it moves it itself.
