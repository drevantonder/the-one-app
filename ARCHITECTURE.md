# Architecture

The node runs on every machine that isn't a phone: laptops, home boxes, work machines. Each is a **server**, with owners and users: it holds `global`, what its owners can read, and the data of each user who trusts it. A server the install owns holds everything and serves everyone: it is **privileged**, because admins trust it, not because of any code. Phones are **clients**: they ask a server and keep nothing but a cache. On a server's machine, the CLI, MCP, a browser and the Mac app's window use that server's local API as its local user. Each context (The One App, a workplace's edition of it) is its own install, with its own CLI, port, keys and data, so someone in several runs several side by side; installs never talk to each other.

Everything lives in a scope: one user's, a group's, or the install's (`global`). Everything anyone does is a signed entry in the author server's log for that scope, and goes only to the servers that hold that scope. Every view is a cache, made by replaying a scope's entries (and `global`'s member entries) in one shared order. The node knows nothing about any app or driver: apps are deployed into the install while it runs, and drivers are installed on the servers whose owners want them.

What's here so far, and what isn't, is at the end ("Built so far").

## Where to look

- `SPEC.md` is the contract between machines. If two must agree on it, it's there.
- `src/entry.rs`: what an entry is, its scope, and the replay order `(time, author, log, seq)`. `PROTOCOL` is the SPEC's version.
- `src/members.rs`: users, groups, roles, servers, ACLs, trust, clients, `open`s, apps, deploys and installs, and so which servers hold which scope and which entries count. Pure: entries in, members out.
- `src/sync.rs`: what two servers say to each other, and which scope goes where: a `Replica` is one server's store and the members its `global` adds up to. It reads and writes the store but has no clock or I/O, so the simulator can drive it.
- `src/store.rs`: every log of every scope this server holds, and the end of each of its own logs, kept when a scope is deleted. It snapshots each scope's views on disk now and then and keeps the last few; an entry that sorts before a view's position rewinds it to the newest snapshot before the entry, or to empty. Snapshots never leave the machine. *(Not built yet: the node keeps views' positions in memory and replays every scope when it starts.)*
- `src/node.rs`: the only place with state and I/O: sessions, pairing codes, readiness, replaying views, loading deploys, where calls run (nearest first, one at a time, the scopes named first) and what each may reach, `open`, hooks, blobs.
- `src/bundle.rs`: a deploy's bundle, a plain tar of `app.js` and `src/`.
- `src/apps.rs`: workerd, which the node downloads (pinned, hash-checked), configures and supervises. `src/runtime/` is what runs inside: a router, and `shim.js` around each deploy's `app.js`, with a Durable Object per app per scope, kept on disk across restarts. It loads each deploy's bundle with workerd's dynamic worker loader, so a deploy needs no restart *(for now the node writes the config again and restarts workerd)*. Each call gets stubs for exactly the scopes it named. `on` handlers see no clock or randomness. Appends are buffered until the call returns.
- `src/native.rs`, `src/builtin.rs`, `src/providers.rs`: drivers as they are for now. Native apps built into the node (`src/shell.rs`, `src/agents.rs`, `src/models.rs`), and providers, programs that register over the local API (the Go ones in `providers/`, the Apple ones in the Mac app). Both serve their server's local user and are advertised in sync with their operations, version and who installed them. A `driver` entry (`members.rs`) removes one from a server, or allows it there again (`<cli> drivers`, and the App Store's Drivers, with `ctx.driver`); `providers/install.sh` writes one as it installs.
- `src/schedules.rs`: apps' schedules: when each slot is (a time of day in a time zone too, with `jiff`), and the line of servers that may run one, worked out from the members alone. The node's schedule loop runs the slots it's first in line for among the servers it can reach, as ordinary calls, and writes a `ran` for each. The loop guards (call depth, and calls and runs per app per minute) are in `src/node.rs`.
- `src/vault.rs`, `src/outbound.rs`: the Vault's items are node entries (`item`), kept in each scope's node state and never in an app's view; an earlier server's `secret` is an item of its own. Workerd's global outbound is a port of the node's own: each request carries its call's token, and the node fills in the fields of the items that call's app is switched on for, a secret field only for its item's hosts, and makes the request itself.
- `src/deploy.rs`: `one deploy <dir>` builds the app with a pinned Bun (downloaded and hash-checked, like workerd), npm packages and all, and tars the bundle with its source; the CLI uploads it and writes the `deploy`. Rolling back is `one deploy <app> --version <hash>`.
- *(Not built yet.)* `src/drivers.rs`: starts the drivers installed on this server, takes registrations over the local API, tells sync whom each serves, and passes them calls.
- *(Not built yet.)* `src/backup.rs`: streams entries and blobs to a bucket, and restores from one.
- `src/update.rs`, `src/release.rs`: tooling, not protocol. `one update` builds main's tip on your own Linux servers and publishes it as a `node-release`, and rebuilds the Mac app on each Mac over SSH; `one release vX.Y.Z` also signs it off (`gh signoff`; there is no CI) and publishes it on GitHub, each file with `<file>.sig`. `install.sh` installs GitHub's latest, if signed with the edition's release key.
- `src/load.rs`: how loaded this machine is (memory, CPU, GPU, disk, the containers it hosts), sampled on a thread of its own and carried in `Hello`. Server info, like `build`, never an entry.
- `src/screen/`: the design kit and the bridge every app screen is served in.
- `src/mcp_apps.rs`, `src/mcp_view.html`: `one mcp` shows widgets and screens inline in chats that support MCP Apps: one `ui://<cli>/view`, filled by the tools `widgets_show` (the trees, drawn in HTML) and `screens_open` (a screen in a frame, its bridge's calls sent back as the app's tools).
- `client/`: the library phones link (Rust, with a C interface in `one_client.h`).
- `apple/`: the Mac app (a server's node inside, its window and menu bar, and the host of the Apple drivers, built in from the `apple-drivers` repo so they keep the permissions macOS grants the app) and the iPhone app and widget (a client). They draw apps' screens and widgets and name no app: a page's Connectors folder is whichever apps keep the connector contract, and every page has one.
- `config.toml`: what's built into the app: the product's name, CLI name, port, accent, icons, release key and signer, the repo `update` gets the code from, the built-in apps a new install deploys and installs in `global` (`apps`), and, for an edition with one install, where its shells sign people in to it (`sign_in`, a work-email join page, and `account`, what they sign in with) instead of offering to start one. Nothing else names the product. Another edition is this code built with its own `config.toml` (`CONFIG=`), in a repo of its own: `update` fetches that repo's latest beside main (`CONFIG_REPO`). What an install does is its **settings** (`setting` entries, admins only, in Settings or `<cli> settings`), over the defaults in `[settings]`: `store`, the app the shells' App Store opens; `push`, the driver phones register with for push (empty: off, and the driver sends nothing); `made_here`, what the App Store calls the apps made in the install; `join_domain`, who may join by signing in with a work email.
- `vendor/`: two iroh dependencies patched so the client builds for iPhone; drop them when upstream builds there.

## Apps it starts with

There are two kinds of app. **Built-in** apps are the folders in `apps/`: every release has all of them (each a plain `app.js`, no build step), any install's App Store lists them, and an admin adds one, as an ordinary app owned by `admins`, deployed from the release's copy. **Made here**: everything else, deployed by an install's own people with `one deploy` from wherever its code lives: a repo in the install, on GitHub, or nowhere. CI, if any, is an app or agent that deploys. *(The native apps and the Go providers are here too, for now.)*

- **Board**, **Agents**, **Shell**, **Models**, **Desktops**, **WhatsApp**, **Messenger** (through a desktop's browser), and the Apple apps (iMessage, Reminders, Calendar, Contacts): apps, with drivers where they need native code (a shell, a local model, Incus, WhatsApp's linked session, macOS frameworks). The Apple drivers live in the Mac app. Each is a built-in app (`apps/<name>`) over a driver of its name: each operation is the driver's, called with `ctx.drivers`, screens are the app's, and an app with no picture of its own shows the one its driver gives (an Apple app's icon); an app installs where no server runs its driver, and says so. *(Where an install hasn't added the app, the driver's own description, operations and screens stand in for it, as Push's and Work email join's always do.)*
- **Browser profiles**: Desktops keeps them (Personal, PTC), each a browser's own cookies and sign-ins, saved on the server that keeps it; a borrowed desktop's browser starts with a copy of one. Desktops is an app with a page, not a connector. Messenger's accounts are the profiles it's linked to (`profiles.json` in its folder; before profiles, the default one).
- **Agents on your own devices**: a device whose owner lets agents use it is a computer in Desktops beside the desktops, under its server's name, with the same `tools`, `use` and `screen`, for the owner's own agents only (a driver serves its server's local user). The Mac app hosts its `computer` driver (`apple/Mac/Providers/Computer.swift`): Cua Driver run as the app's child, embedded, so the Accessibility and Screen Recording permissions are the app's, granted once. A driver of its own, not the desktops driver's, because only the Mac app can hold those permissions, and the desktops driver isn't on every Mac. It's off until the owner turns it on, in the menu bar's panel or on the Desktops page, which asks at the Mac before it's on; while an agent uses it, the menu bar says who, with Stop, which turns it off and stops Cua Driver at once. Desktops logs each session as a `session` entry in the person's scope (who, which device, when) and shows them. Linux devices with a screen would take a driver with the same operations; none of ours has one, so there isn't one yet. iPhones and iPads can't be used: iOS doesn't let one app control others.
- **WhatsApp**: a connector; each linked phone is a session with its own database in the driver's folder, `whatsapp.db` the first (the only one before several) and `whatsapp-<time>.db` each since. Each is on one server, and moves alone.
- **Gmail**, **Google Drive**, **Google Calendar**, **Google Sheets** and **Google Docs** (`apps/gmail`, `drive`, `google-calendar`, `sheets`, `docs`): pure apps: the internet and the Vault, no driver. They share what signing in needs, as Vault items sent only to Google's token address: one "Google sign-in" (the OAuth client's id and secret) and a "Google account" for each account (its address, refresh token and the scopes it allowed), so an account signed in once serves each Google app switched on for it, signing in again only to allow that app's scopes (incremental consent). A sign-in's verifier waits in the app's own data. They're connectors (SPEC.md "Connectors"), for agents and other apps rather than mail or calendar apps, so the shells keep them in each page's Connectors folder, and they never badge or push. Each app's copy of the signing in and the settings screen is the same; there's no shared code between apps.
- **Devices** (`apps/devices`): each server's load and containers, from `ctx.servers()`; no driver, since each node measures itself.
- **Remote MCP servers** (`apps/mcp`): `apps/mcp/add <name> <url>` makes one an app from `template.js`, its tools as operations forwarded over streamable HTTP, with MCP's OAuth and several accounts, each a Vault item holding its tokens; run again, it deploys the server's tools as they are now. Apps can't deploy, so it's a script beside the CLI.
- **Push** (`providers/push`, Go, APNs over HTTP/2 with the edition's key in its own folder; the install's `push` setting): as on iOS, each app counts what waits for you on its own icon (`badge(ctx)`), and pushes for itself with `ctx.drivers.push.send`; agents with `push_send`. A privileged server runs the driver for everyone: phones register their tokens with it (it keeps them in its folder), a push goes to the caller's own phones, and the node tells it which app sent it, whose screen a tap opens. It reports how many APNs accepted, never whether anyone saw it. The install's own requests (joining, secrets asked for) are counted on Settings, and a schedule that failed its last run on the App Store's icon.
- **Work email join** (`providers/workjoin`, Go): people join by signing in with Google on one domain (a workplace's) instead of being handed a pairing code. Admins who trust it install it on a privileged server and give it its Google client, and set the install's `join_domain`; it makes each new member's pairing code through that server's local API, as its local user, an admin, and invites them to a group; someone who signs in again gets a code for another of their own machines. Signing in from a shell (the config's `sign_in`) ends at `<cli>://join`, with the code. The node knows nothing of it, and it's off wherever it isn't installed and configured, or while `join_domain` is empty.
- **Repos** (`apps/repos`): git hosting as an ordinary app, installed in `global`, so every repo is visible to everyone. Its entries are `repo { name, owner, from? }` and `push { repo, branch, base, head }` with a pack blob. A branch moves iff `base` is its current head; no git runs in the app. Only the repo's owner (a user, a group, or admins) moves `main` and other bare branches; anyone pushes their own (`main@bob`, after their name), as suggestions, which then are theirs alone to move. A fork (`repo` with `from`) starts with the source's bare branches and packs. Compaction, if a repo ever needs it, is app code. `git-remote-one` (`src/git.rs`, the `one` binary under that name; `install.sh` links it) runs on a machine with a node: local git builds the packs (never thin), and the helper uploads them as blobs and calls the app on its own server through the local API; fetching downloads the packs it hasn't indexed and indexes them. Repo pages are the app's screens: the app reads trees, files, history and diffs out of the packs itself (`git.js`, which indexes a pack the first time it's read and keeps it in memory while the app runs), so pushing never waits for an index.

## Invariants

- Once servers can reach each other again, each holds exactly the scopes it should, and the same entries give the same views on every server (`tests/sim.rs`).
- An entry, once appended, is never lost: any server that holds it passes it on to every server that should hold it.
- A server holds a user's own data only if that user trusts it, and a group's only if its owners can read it.
- No one reads another user's data except by an `open`, which that user sees.
- A call never runs on two servers, reaches only the scopes its user may use, and writes nothing if it fails.
- A key that isn't a current server or client can't sync, call or ask.
- Every app runs its latest deploy, everywhere. A driver runs on a server only if one of its owners installed it.
- A secret field's value leaves the node only inside a request to one of its item's hosts, by an app switched on for that item.
- Privileged servers are trusted by admins, not built in: any server can be made one, and the install keeps working without them.
- The node never names an app or driver.

## Built so far

Slice 1, scopes and servers, is in: entries in scopes, members (users, groups, servers, clients, ACLs, trust, roles, relays, the recovery key's public half), one log per scope per server, sync that sends each server only what it holds and deletes what it no longer should, readiness, calls that name their scopes and fail over, `open`, `app`/`deploy`/`install` and the board as a deployed app, phones as clients, and the simulator and end-to-end tests for all of it.

Slice 2, apps: `one deploy` builds with a pinned Bun, npm packages and all, keeps the source in the bundle for anyone to read (`one source`, `GET /v1/source/<app>`), and rolls back by deploying an older bundle; only someone acting for an app's owner deploys it. The Vault: items set and listed (secret fields never read) by the CLI, API, MCP and calls, asked for with requests a person answers in a sheet, and their fields filled into the requests of the apps switched on for them, secret ones only for their hosts. Apps declare what they `use`, call it with `ctx.apps` and `ctx.drivers`, and installing one installs what it uses; `ctx.blob` and `ctx.catalog`; an app installed in several scopes; forks (`one fork`), with their own data and a `from` link. The repos app and `git-remote-one`: `git clone`, `push` and `fetch` of `one://<repo>`. The App Store (`apps/apps`, the install's `store` setting): every app, who owns it, where it's installed, its forks and its code, and "Add to…" with `ctx.install`. Built-in apps: every folder in `apps/` is in the binary, each kept as a blob when the node starts. `ctx.catalog` lists the ones the install hasn't added too, and installing one adds it first (admins only: a group admin adds one the install has). The App Store shows them under "Built In", added or not, up to date or running another version, and the rest under the install's `made_here` setting. A new install starts with the config's `apps`; `one update`, once this device runs the new build, deploys the release's copy of each built-in app the install has where it runs another, so a deploy by hand lasts until the next update.

Not yet: drivers the node starts from a `driver` entry's executable (`src/drivers.rs`, `/v1/drivers`): `driver` entries only remove a driver from a server or allow it there again, and native apps and providers stand in for the rest; backups, restore and the recovery admit; view snapshots; the dynamic worker loader (workerd restarts on a deploy); seeding repos with the built-in apps' code; moving the native apps and drivers out of this repo; deleting blobs a server no longer needs.
