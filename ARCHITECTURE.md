# Architecture

The map: what lives where, and the few rules the code only shows by keeping them. How each piece works is in the piece, and its tests.

```
 CLI, MCP, agent hooks, git, sidecars       web, MCP clients         Mac app's window, iPhone, Android, Windows (client/)
                   \                               |                                   |
                    \               the kernel's relay, signed in                       |
                     \                       /                                         |
                local HTTP API (src/api.rs) ─────────────────────────────────────────  iroh
                                     \                                                 |
                       node (src/node.rs, src/node/) ─── iroh, through the relay at the install's address (src/node/net.rs)
                        │             │                        │
   store (src/store.rs)       apps (src/apps.rs,       sidecars (src/sidecars.rs)
                              src/runtime/, workerd)
                        │             │
   entry (src/entry.rs) ·     databases (src/db.rs) in the bucket (src/bucket.rs)
   members (src/members.rs) · replica (src/replica.rs)
```

## Rules

- **Six primitives**: key, log, view, blob, call, app. Scopes, devices, deploys, sidecars, the Vault and backups are made of them.
- **Each app's databases are its data; entries are who can do what.** An app's data in a scope is one SQLite database, the truth, kept sealed in the install's bucket; a call's writes are one transaction, written as one step, so devices writing at once lose nothing. How things went (who used an app, its errors and AI cost, schedules' runs, each device's build, backup runs) is rows of the node's own database of a scope, changed in place. Members, devices, deploys, settings and the rest of the node's state of each scope are signed entries in their author's log for one scope (a user's, a group's, or the install's, `global`), kept sealed in the bucket at numbered positions, with a copy of all of them now and then (`src/log.rs`), and replayed with `global`'s member entries in causal order (each after its backlink and the other logs' entries its author had read, never by the time it claims; ties by hash), so the same entries say the same on every device. A member entry counts only if one of its person's own devices signed it; a scope's other entries also when a node that runs that scope's calls did. An entry, once appended, is never lost.
- **Where a scope's calls run is who its devices are.** A node runs (and holds) a person's own scope if it's listed as their device, a group's if it's a device of the group's admins or the install's, and `global` if it's an admin's. No one reads another person's data.
- **A key belongs to one install, forever.** Installs (white labels, workplaces) never talk to each other. A key that isn't a current device or client can't call or ask.
- **The bucket is the truth, and each device on a machine keeps a copy.** Each blob an entry names is in the bucket too, sealed with its scope's key, where a device that lacks one reads it (`src/node/blobs.rs`), a deploy's bundle and a release's binary among them. Devices send each other calls, a hello (their sidecars and load) and a "something changed" notice over iroh, which is only a hint: each reads what changed from the bucket, and reads it anyway now and then. A database's steps are each written once, at a position their seal binds them to, so a device keeps on its disk the steps it reads and writes: a read uses that copy, and asks the bucket first only after a notice whose step it hasn't fetched yet. A notice of a write carries its step (up to a megabyte), which a device keeps only once the bucket confirms it holds those bytes (`Copied::take_sent`), so no device can show another anything but the bucket's. Every 10 seconds each device fills its copy from the bucket, for a notice that was lost. Writes go to the bucket, which decides their order.
- **Devices reach each other over iroh** (`src/node/net.rs`), each the endpoint of its own device key: directly where a path opens (a LAN, a tailnet, a port its router maps by UPnP, NAT-PMP or PCP), otherwise through the relay at the install's address, their only relay, so n0's carry nothing; they're found by the install's list of devices, never n0's discovery. iroh's QUIC is end to end and proves both ends' keys, so a hacked relay can drop what devices say to each other but read, change, replay or pass off none of it; an ask is one stream and its answer comes back on it. A device answers only the install's devices, and a computer joining only its ask to join. The relay lets in only the install's endpoints, and a computer joining with a pairing code that names the install's address, which shows it a ticket the device that made the code told it the hash of.
- **A call runs once.** It names the scopes it touches before it runs, so a device that can't run it says so before doing anything; one that writes takes a lease in the bucket first, so failing over never repeats it. It writes nothing if it fails.
- **Secrets stay put.** A secret field's value leaves the node only inside a request to one of its item's hosts, or a call to a sidecar its hosts name, by an app switched on for that item. Nothing reads one back.
- **The node never names an app or sidecar.** Apps are deployed into the install while it runs, and every app runs its latest deploy, everywhere; sidecars run only where a device's owner installed them.
- **An older device can safely ignore it.** Phones and Macs run behind the devices, so anything machines see changes only in ways an older one can ignore: new fields and kinds are skipped, and old names keep working for as long as something built before sends them.
- **Keys are opened only on people's own devices, and no Worker can open data.** Everything that takes part is an iroh endpoint with its own device key, listed in the install, playing one or more roles: a **client** is what people and agents use (apps, browsers, the MCP Worker) and holds its person's keys for that device; **compute** runs apps against the data and holds no keys (nodes on machines, the serverless node); a **service** offers a device's abilities (WhatsApp's link, iMessage, Reminders, Shell, Computer Use, Agent Devices) to callers over iroh, checking each caller's device key and permission itself. A machine plays several: linux compute and services, a Mac a client and services with no compute, a phone a client.
- **Every client is a device with its own key pair**: a native app's in the Keychain, keystore or Credential Locker, a browser's a non-extractable WebCrypto key in IndexedDB, a local agent's its machine's. No key is shared by a person's devices. A new device gets in only when one of the person's devices approves it, from a code or QR that shows which device it is (as linking WhatsApp Web does), which seals it the keys of the scopes it may open. A person who lost a device is let back in by another; by a copy sealed under a passkey's PRF (optional for most, kept because synced passkeys make it self-service); or with the install's recovery key, kept offline by an admin, each use of it an entry in the log.
- **Each scope has one key at a time.** It changes only when a person, or a device that didn't sign itself out (lost or stolen), is removed: never on sign-out (the device deletes its own key) or when the same machine re-pairs. A change is eager and complete: one admin's client device makes the new key, writes a fresh copy of every database in the scope (and its log) under it, seals it to everyone who still belongs (client devices and live grants), and the old key is dropped. A write racing the change fails on the new position and runs again under the new key, so readers never juggle more than one key. Backups carry their own key, sealed to the recovery key.
- **Signing in proves who you are, nothing more.** Better Auth (passkeys, Google, others later) never opens a key, so faking it opens nothing. Admins sign in with passkeys, which resist phishing and carry their PRF recovery copy; others as the install allows (Google at a workplace). Everyone joins by invite, at a workplace too, never by their email's domain alone: an invite carries a one-time secret, never a key, and the newcomer's first device gets its keys when the inviting admin's device approves it.
- **Access is given by the giver's device, at that moment.** Adding someone to a group: the admin's device seals the group's key to that person's devices. Who can do what is entries signed by a person's device key, which count by who signed them, in causal order by their backlinks (p2panda), never the time they claim. A client replays `global`'s entries itself, with the nodes' own Rust, from the install's first entry it kept when it joined, and seals and hands keys only to whom they list (a scope's key to its people's client devices at their seal keys, a call's keys to a node they say runs it), never as a node says.
- **Nodes hold no keys.** A caller hands a node the database keys one call needs (derived by HKDF), bound to the caller's token and expiring with it. A scope's Vault items are sealed to its Vault key, whose secret half only the machines its admins grant hold (and the recovery key): anyone who uses the scope adds one, nobody else reads one back, and a granted machine fills it in. A scope's calls run only on nodes its owners trust, in Where Things Run's order. Every node on a machine keeps a sealed copy of what it serves. The serverless node is a node like the others, on Cloudflare, with no keys either, and only a fallback: it holds no connection and keeps nothing, and wakes only when called, when no machine's node answers. The relay hands it the packets addressed to it by RPC to its Durable Object, and the MCP Worker reaches it the same way.
- **Standing work** (scheduled work, and services that act as things arrive, like WhatsApp and iMessage writing messages, built-in services' records, a node's status rows and backups) runs on a machine the person chose, with the database keys of that app in that scope sealed to it until they expire, shown plainly and revocable in Settings › Devices ("linux keeps WhatsApp running for you"); nothing runs while it's off. It's the one way an endpoint holds keys it wasn't handed for a call. A service doesn't write itself: it asks compute to, handing it the keys of its grant.
- **Only the URL signer holds the bucket's credentials.** It's a small Worker: it gives create-only and read URLs for a request signed by a device of someone with access to what it names, many in one request (the next positions ahead of time), and checks many ETags at once with its own access to the bucket. Nodes hold none. Each step is created only if absent, at its numbered position, so the bucket stays the order of writes; while it can't be reached, writes wait.
- **Remote MCP clients** while no machine's node is on are answered by the serverless node, for apps that keep to their own data, as it answers their calls.
- **The kernel is a few small Workers**, each holding only its own secrets, none able to open data: the gateway (the install's address, with the web client's files, routing to the rest by service binding), auth (Better Auth), MCP, the serverless node, the relay (its Durable Object) and the URL signer. The gateway serves the code browsers run, so a hacked one could take what browsers open; native apps and agents run none of it. Devices reach nodes over iroh, never through the gateway.
- **Keys decide access; the relay decides who's on the network.** A group's data opens only with its key, so nothing on Cloudflare needs to know who's in what. The one thing it checks is whether an endpoint is one of the install's: the relay's Durable Object keeps the install's allowed endpoint keys (public keys only, and which endpoint let each in), admits only them, and is the one list. A device that approves a new one also tells the relay to let its key in, signed with its own; an admin's device takes one out, with what it let in; the install's first device is added when the install is made. The URL signer asks the relay, by service binding, whether a request's signer is allowed. Better Auth only proves who people are when they sign in.
- **Cloudflare is what the web and MCP trust:** whoever holds the account serves the code browsers run and runs the MCP Worker, as whoever holds a domain does, so the account is guarded with a hardware security key rather than designed around.
- **Speed** is held to targets measured in `one try`, from a phone on mobile data where it matters: the web client usable within 1.5 s of a cold open (iroh's WebAssembly loading while the page draws, one connection per browser shared by every screen); a remote MCP call adding at most 100 ms to a local one (the MCP Worker keeping its connection to a node between calls, in a Durable Object); a write seen on another device within 1 s; a call one round trip (a caller hands the keys it knows with the call); and no data rewritten when someone adds a device. The relay's Durable Object is placed near the install's people, from the white label's settings.

## Where things are

- `src/entry.rs`: what an entry is (signed the same in `kernel/shared/crypto.js`), its scope, and the causal order.
- `src/members.rs`: users, groups, endpoints and their roles, epochs, grants, apps and installs, from `global`'s entries; which nodes run which scope and which entries count. Pure: entries in, members out.
- `src/replica.rs`: what a device holds and knows: the entries of each scope it holds, as the bucket gives them, and the members they add up to. No clock or I/O.
- `src/store.rs`: every log of every scope a device holds, and how far it has read each from the bucket.
- `src/node.rs`, `src/node/`: the only place with state and I/O, as one `Node` whose methods are split by concern into the modules beside `node.rs`: calls, databases, logs, the network, apps, screens, state, the Vault, sidecars, pairing, blobs, releases, status, storage, backups, schedules, standing work and sign-ins' sessions.
- `src/api.rs`: the local HTTP API every shell, the CLI, MCP and sidecars use, what a client device asks over iroh (the CLI and MCP among them, on a computer with no node; `<cli>/http/1`, HTTP/1.1 on a stream of its own per request, as the person whose device the connection proves it is, handing keys for its key), and what this machine's CLI and MCP, signed in at the kernel, ask. A request to `/<app>/…` is the app's `_http` operation, its body a blob: how stock git reaches Repos. A request with a kernel access token for the install's address (this machine's CLI and MCP after `sign-in`; never a remote MCP client's, which is for `<address>/mcp`) is its person's, and so is its call's; someone it's for who isn't a person of the install yet is let in as a member, by a device whose own person is an admin, since the kernel signs in only those an admin invited or people at the install's domain; a request without one is this machine's own programs', over its loopback with the token in the node's home (`local-token`, which only its user reads), or refused, but for a picture a window's app list names by its content (`/v1/images/<name>`), anyone's who has that name.
- `src/apps.rs`, `src/runtime/`: workerd, which runs every app; `src/runtime/shim.js` is what an app's `ctx` is.
- `src/sidecars.rs`: device sidecars: the ones built in (`src/shell.rs`, `src/agents.rs`, `src/models.rs`), which nodes list in their hello; the Mac app's (`apple/Mac/Sidecars`), which still register over the local API; and the rest, each a service endpoint of its own (`src/service.rs`) with no node needed beside it: the ones this program hosts (`one sidecars serve`: `src/push.rs`, `src/messenger.rs`) and those in Go (`sidecars/`, started by `one sidecars host`), which register with it over a loopback as they did with a node. A service is approved by the code it shows, as a device is, learns who may call it from the `global` entries nodes bring it (replayed from the install's first entry, which it's installed with), and asks a node of its person's for what it writes.
- `sidecars/agent-devices`: the devices agents borrow. A program in one reaches nothing of this machine's 127.0.0.1, which is for its own programs: Windows is on passt, Android on Linux in a network of its own (pasta), and `reach` opens one port the asker chose, never the node's, adb's or another device's. On a Mac nothing can do that: an Android phone's apps reach the Mac's 127.0.0.1 at 10.0.2.2, adb's server among it, and an iPhone simulator's share the Mac's network and files, its node's token too.
- `src/vault.rs`, `src/outbound.rs`: the Vault's items, and filling them into apps' and sidecars' requests on the way out.
- `src/db.rs`: an app's database in a scope, as sealed steps in the bucket. No clock, disk or network.
- `src/bucket.rs`, `src/bucket/`: the bucket, a folder or S3-compatible storage, and a device's copy of the databases' steps on its disk.
- `src/backups.rs`: backups' format and places. `src/schedules.rs`: apps' schedules, which run from the node of a machine its person chose to keep the app running (`src/node/standing.rs`: a `grant`, with that app's keys in that scope sealed to it at `<folder>/<app>/_grants/<endpoint>/<epoch>`, and nothing else of the scope), each slot once, and not while it's off.
- `src/state.rs`: the install as one person sees it (`/v1/state`), the same from a node on a machine and the serverless node.
- `src/deploy.rs`, `src/bundle.rs`: `one deploy`, and the bundle it makes, which keeps the app's source.
- `src/screen/`: the design kit and the bridge every app screen is served in, widgets drawn as HTML, and what a web page that holds screens does for them (`host.js`: their look, and its answer to each of the bridge's messages), the web client's and a chat's alike, each giving it only what it does its own way. The clients' own screens are drawn here once, the same on every client: the person's pages (`pages.html`, with arranging and widgets), a page's Services, a request for a Vault item, and Settings' (`settings/`), which act through the bridge's `one.api` as the person looking, so each client makes them from what it ships and never takes them from a node (`src/screen.rs`'s `client_page`: the native apps' through `client/ffi`, the web client's from its address's `screens/`), and answers `one.api` only for a screen it chose to show as its own. A client is a shell around them that answers the bridge, natively for whatever a person touches: menus, alerts, sheets, files, scanning and links. `src/mcp_apps.rs`, `src/mcp_view.html`: widgets and screens drawn inline in chats, as MCP Apps; a chat sends a view nothing it doesn't ask for, so the view asks the node for each change while it's on screen (`screens_changes`), and what a chat's frame can't do (give files) it opens in the web client.
- `src/skills.rs`, `skills/`: what agents are told, as Agent Skills. `src/code.rs`, `src/codemode/`: search, and code mode.
- `src/ops.rs`, `src/main.rs`: the CLI and MCP, over stdio and at `/mcp`, for this machine's own programs and the install's client devices over iroh: the MCP Worker among them, as remote MCP clients' device. The program is a package of its own (`cli/`), since it uses `client/`, which uses this crate: on a computer where no node runs, it's a client device of its person (`src/client_device.rs`), signed in and approved by its code as the apps are, its key beside its sign-in, and asks their nodes over iroh what it'd ask this machine's, of what a node lets a client device ask; the rest says it needs a node here.
- `src/load.rs`, `src/logos.rs`: how loaded a machine is, and the logos of the sites apps connect to.
- `src/update.rs`, `src/release.rs`: building, signing and publishing the node; tooling, not protocol.
- `client/`: how a client device reaches its install's nodes, natively and in browsers as WebAssembly (`client/src/wasm.rs`, for the web client's one SharedWorker): an iroh endpoint of the device's key, or in a browser, whose device key WebCrypto won't give up, of a key of the session's that the device key vouches for for a day at most (`keys::certify`: the relay's auth token, and `x-one-endpoint` on each request, which a node takes as that device), through the relay at the install's address, a connection kept to each node it asks, in Where Things Run's order, and a fresh endpoint once the network comes back. Natively it's also the app as a device of its person (`client/src/device.rs`, the same as `kernel/web/device.js` in a browser): asking to be let in with its code, opening the epochs sealed to it, and handing each request the keys it needed (`x-one-keys`), with the node's own formats and rules (the `one` crate without its `node` feature), checking who's who from `global`'s entries it reads from the bucket itself. `client/ffi/` is it for the native apps, one definition from which uniffi makes their Swift, Kotlin and C# at each app's build.
- `kernel/`: the kernel's services, JavaScript for workerd, each one Worker with one Durable Object: `auth/` (Better Auth: passkeys only, since only a passkey's PRF output opens keys, joined by invite links; or, for a white label whose `sign_in` is `google`, Google only, at its `join_domain`, every time, which people join by doing; and the OAuth server every client signs in through), `relay/` (iroh's relay protocol, iroh-relay's own Rust as WebAssembly in `protos/`, in a Durable Object with WebSocket Hibernation placed near its people by the white label's `relay_location`, asleep between packets: it lets in only the install's endpoints, its one list of them with each one's role, which devices change by signed tells and the URL signer asks by `allowed`, a session's endpoint its device vouches for, until then, and a computer joining with a pairing code's ticket, which reaches only the device that made the code; and tells an endpoint of the install the compute endpoints, a new client's first nodes to ask, at `/relay/computes`, and when each of its devices was last let in, at `/relay/seen`), `mcp/` (remote MCP clients' devices, since ChatGPT and Claude.ai can't run our code: each client a person signs in with is a device of theirs, which they approve by its code like any other, a Durable Object per client and person running its iroh endpoint with no socket, as the serverless node's, bound at the relay while it runs (by the relay's `McpDevices` entrypoint, never its object); its secret is kept only sealed under its client's own tokens, as the Worker is on their token path, re-sealing it at each refresh and dropping the old refresh token's copy; it reads who's who from the bucket itself, as nodes do, asks only the compute endpoints the entries list as running its person's calls, opens the keys a call needs from the bucket, hands each node only those of the scopes it runs and of what that tool needed, never a token, and keeps its connections warm until nobody has asked for 30 s; only it takes a remote MCP client's tokens, which are for `<address>/mcp`: auth gives `<address>`, a sign-in at nodes, only to the install's own apps), and `gateway/`, a Worker with no keys at the install's address: sign-in to auth (passkeys belong to that address), `/mcp` and what MCP clients read to sign in to `mcp/`, `/relay`, `/ping`, `/generate_204`, `/relay/tell`, `/relay/computes` and `/relay/seen` to the relay, and the rest to the web client's files, with `src/screen/`'s at `/screen/`. `web/` is the web client, the Mac app's window in a browser: an OAuth client of auth like any other, its code only ever from the kernel since it holds browsers' tokens, which once it's a device of its person asks their nodes itself over iroh, every tab through one client in a SharedWorker (`net.js`, `net-worker.js`; the client's WebAssembly at `/client/<its hash>/`), handing keys only to the node that answered with a 428 for them, its sidebar beside the clients' own screens and apps', each in a sandboxed frame whose bridge it answers. `shared/crypto.js` is the formats nodes read too.
- `serverless/`: the serverless node, a node as a Worker in the kernel's Cloudflare account, asked over iroh like any node. `worker.js` checks each request's sign-in, opens the keys its caller hands it for the databases a call reaches (`x-one-keys`, sealed to its endpoint; 428 with what it needs, as a node on a machine answers; kept with the sign-in until its token expires or the log says its person lost a scope), reads the bucket through the URL signer's URLs, signed by its endpoint key, keeping what it read sealed in its Durable Object's storage (every name but a database's `newest` is created once, so what's kept is never stale and a wake fetches only what's newer), runs the app in an isolate of its own (Worker Loader, with `src/runtime/shim.js`), and writes what it wrote, telling nobody: devices read it from the bucket; `serverless/src/lib.rs` is the node's own Rust (the `one` crate) as WebAssembly, with SQLite compiled in, since SQLite's JavaScript build makes WebAssembly at runtime, which Workers forbid. It reads who can do what from the install's log, and each app's latest deploy, from the bucket; an app's requests go out through the vault, which fills in its Vault items. It runs the calls of apps that keep to their own data, and sends the rest on to a node on a machine, over iroh; when none answers, it answers the install's state, apps, widgets and badges, and runs any app that needs no sidecar, itself. A call goes only to a node that runs every scope it reaches for its person, with only those scopes' keys, sealed to that node for the serverless node's key, and never the sign-in's token. Each person's requests run in a Durable Object of their own (`Node` named `user:<id>`), which alone holds what they handed and opened with it (databases, entries, apps' isolates, its copy of the bucket), sharing an open database only between calls handed exactly the keys it was opened with, and writing only under a scope's signed current epoch. The object named `node` is its iroh endpoint, of its own key (`serverless/src/net.rs`, iroh with a transport of its own and no socket): the relay hands it, by RPC, the datagrams sent to that key, waking it, and sends on what it sends; it passes each ask to the asker's person's object, asks devices for calls in Where Things Run's order, keeping its connections while it lives, and ends itself once nobody has asked for 30 s, since iroh's timers would keep it awake, and billed, for good. `src/serverless.rs` deploys it; `update` builds its WebAssembly into the release.
- `src/kernel.rs`: the kernel as nodes meet it: the same formats, checking access tokens, and building the services with the pinned Bun and running them in workerd.
- `apple/`: the Mac app (a device's node inside, the Apple sidecars, and its window, a client as the iPhone is, which the Mac's own node approves at once if it's its person's, and which until signed in shows only its sign-in screen: the person's default browser for the passkey, back at a loopback port as on Windows) and the iPhone app and widget (a client: the system's sign-in sheet for the passkey, back at `<cli>://signed-in/`, the refresh token and its device key in the Keychain, asking the person's nodes over iroh through `client/ffi`). Both are a shell around the clients' own screens and apps', each in a web view whose bridge it answers (`AppScreen.swift`): the Mac's window has a native sidebar picking a page, and the iPhone swipes between its pages as its home; the Mac's menu bar and the iPhone's home screen draw widgets natively (`WidgetTree.swift`).
- `android/`: the Android app, a client that signs in through the kernel's auth service as the web client does (a Custom Tab for the passkey, back at `<cli>://signed-in/`), its refresh token and device key sealed by the phone's keystore, asking the person's nodes over iroh through `client/ffi`: a shell around the clients' own screens and apps', each in a web view of its own whose bridge it answers, its pages (swiped between) as its home; the home screen's widgets drawn natively.
- `windows/`: the Windows app, the Mac app's window on Windows (WinUI 3), a client that signs in through the kernel's auth service as the web client does (in the person's browser, back at a port on the computer, RFC 8252), its refresh token and device key in Windows' Credential Locker, asking the person's nodes over iroh through `client/ffi`, its sidebar beside the clients' own screens and apps', each in a WebView2 of its own whose bridge it answers, with Windows' own menus, dialogs and sheets, and the Widgets board's widgets drawn as Adaptive Cards.
- `apps/`: the built-in apps, which every release ships and a new install has (added by its admin), so anyone may put one on their own page; a later release's new ones its admins add. Everything else is deployed by an install's own people.
- `config.toml`: the white label: its name, CLI, port, icons, release key, starter apps, and how its people sign in. Nothing else names the product.
- `tests/`: `sim.rs`, many devices writing one database in one bucket over bad links; `e2e.rs`, real nodes; `kernel.rs`, the kernel's services in workerd (and `kernel/test/`); `contracts.rs`, wherever two languages must agree; `agents/`, fresh agents doing everyday tasks.
- `vendor/phosphor/`: Phosphor's icons, which apps name and every client draws.

## Designed, not built

- Backups' recovery from nothing: a device restoring with no one left to pair with admits itself with the recovery key's countersignature.
- Sidecars a node starts from a `sidecar` entry's executable, rather than registering themselves.
- Services each running as their own OS user per scope, and Shell and Computer Use only with a grant for that device and session, approved by the person.
- Native apps keeping their own sealed copy, for reads with no network; writes while offline, replayed like a rebase, never repeating what went outside.
