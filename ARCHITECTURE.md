# Architecture

The map: what lives where, and the few rules the code only shows by keeping them. How each piece works is in the piece, and its tests.

```
 Mac app's window, CLI, MCP, agent hooks, git, sidecars       web, iPhone, Android, Windows, MCP clients
                         \                                                 |
                          \                                 the kernel's gateway, signed in
                           \                                    /
                local HTTP API (src/api.rs) ─────────────────────
                                     \
                       node (src/node.rs, src/node/) ─── iroh, through the relay at the install's address (src/node/net.rs)
                        │             │                        │
   store (src/store.rs)       apps (src/apps.rs,       sidecars (src/sidecars.rs)
                              src/runtime/, workerd)
                        │             │
   entry (src/entry.rs) ·     databases (src/db.rs) in the bucket (src/bucket.rs)
   members (src/members.rs) · replica (src/replica.rs)
```

## Rules

- **Six primitives**: key, log, view, blob, call, app. Scopes, devices, deploys, sidecars, the Vault and backups are made of them.
- **Each app's databases are its data; entries are who can do what.** An app's data in a scope is one SQLite database, the truth, kept sealed in the install's bucket; a call's writes are one transaction, written as one step, so devices writing at once lose nothing. How things went (who used an app, its errors and AI cost, schedules' runs, each device's build, backup runs) is rows of the node's own database of a scope, changed in place. Members, devices, deploys, settings and the rest of the node's state of each scope are signed entries in their author's log for one scope (a user's, a group's, or the install's, `global`), kept sealed in the bucket at numbered positions, with a copy of all of them now and then (`src/log.rs`), and replayed with `global`'s member entries in causal order (each after its backlink and the other logs' entries its author had read, never by the time it claims; ties by hash), so the same entries say the same on every device. A member entry counts only if one of its person's own devices signed it; a scope's other entries also when a node that runs that scope's calls did. An entry, once appended, is never lost.
- **Where a scope's calls run is who its devices are.** A node runs (and holds) a person's own scope if it's listed as their device, a group's if it's a device of the group's admins or the install's, and `global` if it's an admin's. No one reads another person's data.
- **The kernel opens nothing alone, where people sign in with passkeys.** Its vault keeps every key sealed under clients' secrets (a passkey's PRF output, an OAuth client's refresh token). A workplace that can't move its people to passkeys signs them in with Google (`sign_in = "google"`), and its vault opens a person's keys itself once auth says Google signed them in: **there a hacked kernel can read all of its data.** Either way it's off the path of a read: it's asked to sign in, to refresh a token, to change who can do what, for a sign-in's keys and bucket URLs, and by schedules.
- **A key belongs to one install, forever.** Installs (white labels, workplaces) never talk to each other. A key that isn't a current device or client can't call or ask.
- **The bucket is the truth, and each device on a machine keeps a copy.** Each blob an entry names is in the bucket too, sealed with its scope's key, where a device that lacks one reads it (`src/node/blobs.rs`), a deploy's bundle and a release's binary among them. Devices send each other calls, a hello (their sidecars and load) and a "something changed" notice over iroh, which is only a hint: each reads what changed from the bucket, and reads it anyway now and then. A database's steps are each written once, at a position their seal binds them to, so a device keeps on its disk the steps it reads and writes: a read uses that copy, and asks the bucket first only after a notice whose step it hasn't fetched yet. A notice of a write carries its step (up to a megabyte), which a device keeps only once the bucket confirms it holds those bytes (`Copied::take_sent`), so no device can show another anything but the bucket's. Every 10 seconds each device fills its copy from the bucket, for a notice that was lost. Writes go to the bucket, which decides their order.
- **Devices reach each other over iroh** (`src/node/net.rs`), each the endpoint of its own device key: directly where a path opens (a LAN, a tailnet, a port its router maps by UPnP, NAT-PMP or PCP), otherwise through the relay at the install's address, their only relay, so n0's carry nothing; they're found by the install's list of devices, never n0's discovery. iroh's QUIC is end to end and proves both ends' keys, so a hacked relay can drop what devices say to each other but read, change, replay or pass off none of it; an ask is one stream and its answer comes back on it. A device answers only the install's devices, and a computer joining only its ask to join. The relay lets in only the install's endpoints, and a computer joining with a pairing code that names the install's address, which shows it a ticket the device that made the code told it the hash of.
- **A call runs once.** It names the scopes it touches before it runs, so a device that can't run it says so before doing anything; one that writes takes a lease in the bucket first, so failing over never repeats it. It writes nothing if it fails.
- **Secrets stay put.** A secret field's value leaves the node only inside a request to one of its item's hosts, or a call to a sidecar its hosts name, by an app switched on for that item. Nothing reads one back.
- **The node never names an app or sidecar.** Apps are deployed into the install while it runs, and every app runs its latest deploy, everywhere; sidecars run only where a device's owner installed them.
- **An older device can safely ignore it.** Phones and Macs run behind the devices, so anything machines see changes only in ways an older one can ignore: new fields and kinds are skipped, and old names keep working for as long as something built before sends them.

## Where things are

- `src/entry.rs`: what an entry is (signed the same in `kernel/shared/crypto.js`), its scope, and the causal order.
- `src/members.rs`: users, groups, endpoints and their roles, epochs, grants, apps and installs, from `global`'s entries; which nodes run which scope and which entries count. Pure: entries in, members out.
- `src/replica.rs`: what a device holds and knows: the entries of each scope it holds, as the bucket gives them, and the members they add up to. No clock or I/O.
- `src/store.rs`: every log of every scope a device holds, and how far it has read each from the bucket.
- `src/node.rs`, `src/node/`: the only place with state and I/O, as one `Node` whose methods are split by concern into the modules beside `node.rs`: calls, databases, logs, the network, apps, screens, state, the Vault, sidecars, pairing, blobs, releases, status, storage, the tunnel, backups, schedules and sign-ins' sessions.
- `src/api.rs`: the local HTTP API every shell, the CLI, MCP and sidecars use, and what clients signed in at the kernel ask through the gateway. A request to `/<app>/…` is the app's `_http` operation, its body a blob: how stock git reaches Repos. A request with a kernel access token (a browser's, through the gateway, or this machine's Mac app window, or its CLI and MCP after `sign-in`) is its person's, and so is its call's; someone it's for who isn't a person of the install yet is let in as a member, by a device whose own person is an admin, since the kernel signs in only those an admin invited or people at the install's domain; a scheduled run's token reaches only `/v1/kernel/run`; a request without one is this machine's own programs', over its loopback with the token in the node's home (`local-token`, which only its user reads), or refused.
- `src/apps.rs`, `src/runtime/`: workerd, which runs every app; `src/runtime/shim.js` is what an app's `ctx` is.
- `src/sidecars.rs`: device sidecars: the ones built in (`src/shell.rs`, `src/agents.rs`, `src/models.rs`), and those that register over the local API: the ones this program hosts as a process of their own (`one sidecars serve`: `src/push.rs`, `src/messenger.rs`), those in Go (`sidecars/`), and the Mac app's (`apple/Mac/Sidecars`).
- `sidecars/agent-devices`: the devices agents borrow. A program in one reaches nothing of this machine's 127.0.0.1, which is for its own programs: Windows is on passt, Android on Linux in a network of its own (pasta), and `reach` opens one port the asker chose, never the node's, adb's or another device's. On a Mac nothing can do that: an Android phone's apps reach the Mac's 127.0.0.1 at 10.0.2.2, adb's server among it, and an iPhone simulator's share the Mac's network and files, its node's token too.
- `src/vault.rs`, `src/outbound.rs`: the Vault's items, and filling them into apps' and sidecars' requests on the way out.
- `src/db.rs`: an app's database in a scope, as sealed steps in the bucket. No clock, disk or network.
- `src/bucket.rs`, `src/bucket/`: the bucket, a folder or S3-compatible storage, and a device's copy of the databases' steps on its disk.
- `src/backups.rs`: backups' format and places. `src/schedules.rs`: apps' schedules, which the kernel's schedules service runs.
- `src/state.rs`: the install as one person sees it (`/v1/state`), the same from a node on a machine and the serverless node.
- `src/deploy.rs`, `src/bundle.rs`: `one deploy`, and the bundle it makes, which keeps the app's source.
- `src/screen/`: the design kit and the bridge every app screen is served in, and widgets drawn as HTML. The clients' own screens are drawn here once, the same on every client: the person's pages (`pages.html`, with arranging and widgets), a page's Services, a request for a Vault item, and Settings' (`settings/`), served as app screens are but with no app (`src/screen.rs`): they act through the bridge's `one.api`, as the person looking, which a client answers only for them. A client is a shell around them that answers the bridge, natively for whatever a person touches: menus, alerts, sheets, files, scanning and links. `src/mcp_apps.rs`, `src/mcp_view.html`: widgets and screens drawn inline in chats.
- `src/skills.rs`, `skills/`: what agents are told, as Agent Skills. `src/code.rs`, `src/codemode/`: search, and code mode.
- `src/ops.rs`, `src/main.rs`: the CLI and MCP, over stdio and at `/mcp`, where MCP clients elsewhere reach a node through the gateway, as the person they signed in as.
- `src/load.rs`, `src/logos.rs`: how loaded a machine is, and the logos of the sites apps connect to.
- `src/update.rs`, `src/release.rs`: building, signing and publishing the node; tooling, not protocol.
- `kernel/`: the kernel's services, JavaScript for workerd, each one Worker with one Durable Object: `auth/` (Better Auth: passkeys only, since only a passkey's PRF output opens keys, joined by invite links; or, for a white label whose `sign_in` is `google`, Google only, at its `join_domain`, every time, which people join by doing; and the OAuth server every client signs in through), `vault/` (every scope's keys and the Vault's items, sealed; keys, filled-in requests and bucket URLs for what a call names; where people sign in with Google, each person's keys sealed under its own key too, which it opens itself once auth says Google signed them in), `schedules/` (fires the schedules people let run while they're away, each run once, with only the keys it was let use), `relay/` (iroh's relay protocol, iroh-relay's own Rust as WebAssembly in `protos/`, in a Durable Object with WebSocket Hibernation placed near its people by the white label's `relay_location`, asleep between packets: it lets in only the install's endpoints, its one list of them, which devices change by signed tells and the URL signer asks by `allowed`, and a computer joining with a pairing code's ticket, which reaches only the device that made the code), and `gateway/`, a Worker with no keys at the install's address: sign-in to auth (passkeys belong to that address), `/v1/` and `/mcp` to a node, stamped so nothing a node says runs at that origin, `/relay`, `/ping`, `/generate_204` and `/relay/tell` to the relay, and the rest to the web client's files, with `src/screen/`'s at `/screen/`. `web/` is the web client, the Mac app's window in a browser: an OAuth client of auth like any other, its code only ever from the kernel since it holds browsers' tokens, its sidebar beside the clients' own screens and apps', each in a sandboxed frame whose bridge it answers. `shared/crypto.js` is the formats nodes read too.
- `serverless/`: the serverless node, a node as a Worker in the kernel's Cloudflare account, which the gateway sends `/v1/` and `/mcp` to by service binding. `worker.js` checks each request's sign-in, asks the vault for the keys and bucket URLs of what a call names (keeping a sign-in, with its keys, until its token expires or the log says its person lost a scope), runs the app in an isolate of its own (Worker Loader, with `src/runtime/shim.js`), and writes what it wrote, telling nobody: devices read it from the bucket; `serverless/src/lib.rs` is the node's own Rust (the `one` crate) as WebAssembly, with SQLite compiled in, since SQLite's JavaScript build makes WebAssembly at runtime, which Workers forbid. It reads who can do what from the install's log, and each app's latest deploy, from the bucket; an app's requests go out through the vault, which fills in its Vault items. It runs the calls of apps that keep to their own data, and sends the rest on to a node on a machine, calls over iroh and the rest through the Tunnel; when none answers, it answers the install's state, apps, widgets and badges, and runs any app that needs no sidecar, itself. Its `Node`, one Durable Object, is its iroh endpoint, of its own key (`serverless/src/net.rs`, iroh with a transport of its own and no socket): the relay hands it, by RPC, the datagrams sent to that key, waking it, and sends on what it sends; it answers asks as `/v1/call`, asks devices for calls in Where Things Run's order, keeping its connections while it lives, and ends itself once nobody has asked for 30 s, since iroh's timers would keep it awake, and billed, for good. `src/serverless.rs` deploys it; `update` builds its WebAssembly into the release.
- `src/kernel.rs`: the kernel as nodes meet it: the same formats, checking access tokens, asking the vault, and building the services with the pinned Bun and running them in workerd.
- `apple/`: the Mac app (a device's node inside, the Apple sidecars, and its window, a client that signs in through the kernel's auth service as the iPhone does and asks the Mac's own node with its token) and the iPhone app and widget (a client: the system's sign-in sheet for the passkey, back at `<cli>://signed-in/`, the refresh token in the Keychain, asking the install's address).
- `android/`: the Android app, a client that signs in through the kernel's auth service as the web client does (a Custom Tab for the passkey, back at `<cli>://signed-in/`), its refresh token sealed by the phone's keystore: a shell around the clients' own screens and apps', each in a web view of its own whose bridge it answers, its pages (swiped between) as its home; the home screen's widgets drawn natively.
- `windows/`: the Windows app, the Mac app's window on Windows (WinUI 3), a client that signs in through the kernel's auth service as the web client does (in the person's browser, back at a port on the computer, RFC 8252), its refresh token in Windows' Credential Locker, its sidebar beside the clients' own screens and apps', each in a WebView2 of its own whose bridge it answers, with Windows' own menus, dialogs and sheets, and the Widgets board's widgets drawn as Adaptive Cards.
- `apps/`: the built-in apps, which every release ships and any install's admins may add. Everything else is deployed by an install's own people.
- `config.toml`: the white label: its name, CLI, port, accent, icons, release key, starter apps, and how its people sign in. Nothing else names the product.
- `tests/`: `sim.rs`, many devices writing one database in one bucket over bad links; `e2e.rs`, real nodes; `kernel.rs`, the kernel's services in workerd (and `kernel/test/`); `contracts.rs`, wherever two languages must agree; `agents/`, fresh agents doing everyday tasks.
- `vendor/phosphor/`: Phosphor's icons, which apps name and every client draws.

## Being built

The design decided on 2026-11-03: keys are opened only on people's own devices, no Worker can open data, and a node has only what a call hands it. It replaces the vault opening keys, device trust, replay and the Tunnel. As each part lands, the rules and map above are rewritten to match and its line here goes.

- **Endpoints and roles.** Everything that takes part is an iroh endpoint with its own device key, listed in the install: one kind of endpoint, playing one or more roles. A **client** is what people and agents use (apps, browsers, the MCP Worker) and holds its person's keys for that device. **Compute** runs apps against the data and holds no keys (nodes on machines, the serverless node). A **service** offers a device's abilities (WhatsApp's link, iMessage, Reminders, Shell, Computer Use, Agent Devices) to callers over iroh, checking each caller's device key and permission itself. A machine plays several: linux compute and services, a Mac a client and services with no compute, a phone a client.
- **Devices.** Every client is a device with its own key pair: a native app's in the Keychain, keystore or Credential Locker, a browser's a non-extractable WebCrypto key in IndexedDB, a local agent's its machine's. No key is shared by a person's devices. A new device gets in only when one of the person's devices approves it, from a code or QR that shows which device it is (as linking WhatsApp Web does), which seals it the keys of the scopes it may open. A person who lost a device is let back in by another; by a copy sealed under a passkey's PRF (optional for most, kept because synced passkeys make it self-service); or with the install's recovery key, kept offline by an admin, each use of it an entry in the log.
- **Epochs.** Each scope's key is numbered. Removing a person or a device seals a new epoch to the devices still allowed; adding one seals it the current epoch, since every browser is a device and a new sign-in mustn't rewrite anything. Every step and entry names the epoch it's sealed under, so a removed or stolen device opens nothing written after. A node writes with the newest at once, and starts each database (and the scope's log) over from a copy under it at its next routine copy, never inside a write; an epoch no database's newest copy is under is erased, which ends what came before for backups and the removed alike.
- **Signing in proves who you are, nothing more.** Better Auth (passkeys, Google, others later) never opens a key, so faking it opens nothing. Admins sign in with passkeys, which resist phishing and carry their PRF recovery copy; others as the install allows (Google at a workplace).
- **Access is given by the giver's device, at that moment.** Adding someone to a group: the admin's device seals the group's current epoch to that person's devices. An invite carries a one-time secret, never a key: the newcomer's first device gets its keys when the inviting admin's device approves it. Everyone joins by invite, at a workplace too, never by their email's domain alone.
- **Who can do what** is entries signed by a person's device key, which count by who signed them and the epoch they're in, not by trusting the device that wrote them, in causal order by their backlinks (p2panda), never the time they claim. Device trust and privileged devices go.
- **Nodes hold no keys.** A caller hands a node the database keys one call needs (derived by HKDF as now, with their epoch), bound to the caller's token and expiring with it; Vault items are sealed per scope like data and handed the same way to a call that fills one in. A scope's calls run only on nodes its owners trust, in Where Things Run's order. Every node on a machine keeps a sealed copy of what it serves. The serverless node is a node like the others, on Cloudflare, with no keys either, and only a fallback: it holds no connection and keeps nothing, and wakes only when called, when no machine's node answers (Cloudflare's place in Where Things Run). The relay hands it the packets addressed to it by RPC to its Durable Object, and the MCP Worker reaches it the same way.
- **Standing work** (scheduled work, and services that act as things arrive, like WhatsApp and iMessage writing messages, built-in services' records, a node's status rows and backups) runs on a machine the person chose, with the database keys of that app in that scope sealed to it until they expire, shown plainly and revocable in Settings › Devices ("linux keeps WhatsApp running for you"); nothing runs while it's off. It's the one way an endpoint holds keys it wasn't handed for a call. A service doesn't write itself: it asks compute to, handing it the keys of its grant.
- **The bucket** (R2) stays the one truth and the order of writes: each step is created only if absent, at its numbered position. Only the URL signer, a small Worker, holds the bucket's credentials: it gives create-only and read URLs for a request signed by a device of someone with access to what it names, many in one request (the next positions ahead of time), and checks many ETags at once with its own access to the bucket. Nodes hold none.
- **Sync.** Once a write lands, the node that wrote it sends the sealed step to the other nodes over iroh, whose QUIC proves who sent it; each applies it only once the bucket confirms that position's ETag (a burst in one check, through the URL signer), and reads the bucket itself only to catch up. While the bucket can't be reached, writes wait.
- **The network is iroh**, between every endpoint: native apps, compute, services and the Workers that act as clients or compute: direct on the LAN, otherwise through the relay. Browsers and the MCP Worker, which have no UDP, run it as WebAssembly, always through the relay. Nodes find each other from the install's list of devices, not n0's discovery. The Cloudflare Tunnel, cloudflared, the gateway's own relay protocol and its passing on of `/v1` go.
- **Remote MCP clients** (ChatGPT, Claude.ai) can't run our code, so the MCP Worker is their device, a client like any other: it speaks MCP to them over HTTPS, keeps their copy of the keys sealed under their rotating single-use refresh token, opens it only while they call, and hands a node a call's database keys: the serverless node by service binding, a machine's over iroh. Their access is any client's.
- **The kernel is seven Workers**, each holding only its own secrets, none able to open data: the gateway (the install's address, routing to the rest by service binding), web (the web client's files), auth (Better Auth), MCP, the serverless node, the relay (its Durable Object) and the URL signer. The gateway and web serve the code browsers run, so a hacked one could take what browsers open; native apps and agents run none of it.
- **Services** (today's sidecars) need no node on their machine: each is an iroh endpoint, or behind a small service host (the node's own program running only that role) where it isn't Rust, as the Go sidecars aren't; the Mac's, in Swift, use iroh through the apps' shared Rust library. App code reaches a service wherever it is. Each runs as its own OS user per scope. Shell and Computer Use run only with a grant for that device and session, approved by the person.
- **Keys decide access; the relay decides who's on the network.** A group's data opens only with its epoch key, and a step not sealed under the scope's current epoch is skipped by every reader, the next write taking the following position; so nothing on Cloudflare needs to know who's in what. The one thing it checks is whether an endpoint is one of the install's: the relay's Durable Object keeps the install's allowed endpoint keys (public keys only, and which endpoint let each in), admits only them, and is the one list. A device that approves a new one also tells the relay to let its key in, signed with its own; an admin's device takes one out, with what it let in; the install's first device is added when the install is made. The URL signer asks the relay, by service binding, whether a request's signer is allowed. Better Auth only proves who people are when they sign in.
- **Cloudflare is what the web and MCP trust:** whoever holds the account serves the code browsers run and runs the MCP Worker, as whoever holds a domain does, so the account is guarded with a hardware security key rather than designed around.
- **Speed** is held to targets measured in `one try` before the cutover, from a phone on mobile data where it matters: the web client usable within 1.5 s of a cold open (iroh's WebAssembly loading while the page draws, one connection per browser shared by every screen); a remote MCP call adding at most 100 ms to a local one (the MCP Worker keeping its connection to a node between calls, in a Durable Object); a write seen on another device within 1 s; a call one round trip (a caller hands the keys it knows with the call); and no data rewritten when someone adds a device. The relay's Durable Object is placed near the install's people, from the white label's settings.
- **Later:** native apps keeping their own sealed copy, for reads with no network; writes while offline, replayed like a rebase, never repeating what went outside.

### What goes, and the order

Goes: sidecars registering with a node on their machine over the local API, the vault Worker and its opening of keys, the schedules Worker, the Tunnel and cloudflared, the gateway's relay protocol and its passing on of `/v1`, device trust and privileged devices, replay in the order entries claim, joining by domain, nodes' scope keys and bucket credentials, and Vault items in the log as secrets nodes read (sealed per scope instead).

1. Prototypes: the relay in a Durable Object, and iroh between nodes and from a browser.
2. Keys: device keys, epochs, signed entries, Better Auth for identity only, the URL signer, invites and approving devices, admins' passkeys and PRF recovery.
3. iroh between every endpoint (compute and services, sidecars moving to service endpoints), and pushing steps.
4. Clients over iroh: one Rust library shared by the native apps, and the same as WebAssembly in browsers.
5. The serverless node woken by the relay and the MCP Worker, and the MCP Worker as remote MCP clients' device.
6. The Tunnel, the vault and the schedules Worker are deleted.

## Designed, not built

- Backups' weekly restore check and recovery from nothing: a device restoring with no one left to pair with admits itself with the recovery key's countersignature.
- Sidecars a node starts from a `sidecar` entry's executable, rather than registering themselves.
