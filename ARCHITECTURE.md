# Architecture

Your devices, and your team's, as one place for apps and agents. A network is one user's or one workplace's: its users, their devices, their apps, and a bucket (a folder or S3-compatible storage) holding everything, sealed. Every machine in it runs the same program; at its address, a few small Workers on Cloudflare, each named by its job, route, sign in, relay, carry pushes, sign bucket URLs and keep telemetry. Two Workers are not like those: the remote MCP server is a client, and the Cloudflare node is a node. Each app's database for a scope is the truth, kept as signed steps in the bucket, and who can do what is the scope database's rows.

It's held to targets measured in `one-dev throwaway`, from a phone on mobile data where it matters: the web client usable within 1.5 s of a cold open; a remote MCP call adding at most 100 ms to a local one; a write seen on another device within 1 s; a call one round trip; no data rewritten when someone adds a device.

This page holds only what the code can't say. How each part works is its folder's doc: `cargo test map -- --nocapture` prints them all, as a map. `tests/contracts.rs` is where two languages must agree.

## Trust

- **Keys are opened only on clients**, the devices of users and their agents (apps, browsers, the CLI, the remote MCP server). **Nodes** run calls and hold no keys: a caller hands a node the database keys one call needs, which expire within the hour. The only exceptions are app schedules and the Vault, where a user or an admin chooses a machine to hold keys and can take them back, and a computer that is also its user's client device: its app runtime opens that user's scopes with what the device's key, held by its onet, opens, for its CLI, its local MCP server and its schedules, and never opens anyone else's that way. So a hacked computer gives up its own user's data, as any of their devices would; for everyone else it's still only the calls it ran while it was hacked. A computer is one device with one key, its onet's: its desktop app's window, the CLI and the local MCP server come with or set up its `oned` and are its onet's own programs, with no key or network of their own, and with no `oned` running on a computer, they say what to install or start.
- **The Workers at the address open no user data.** A hacked node gets only the calls it ran while it was hacked; a hacked gateway, auth, relay, URL signer, push or telemetry Worker reads no user data. Telemetry is operational and unsealed (Andre, 11-10): closed-set names and numbers, and the scrubbed message of a real failure, which we treat as operational and which the telemetry Worker, Cloudflare and any device in the network can read. Who made a call is operational too (Andre, 11-11): its span names its user by their id (OTEL's `enduser.id`), recorded unsealed, and Insights is where who uses an app is seen. The Workers that serve browsers' code could take what browsers open, which is why they stay small, and why the Cloudflare account is guarded with a hardware security key. The remote MCP server is the same: its devices' secrets are sealed under their MCP clients' tokens, which reach it on every call, so whoever can change its code could open the keys of the scopes those devices were approved for. We consider it as secure as our Cloudflare account (Andre, 2026-11-05). The other Workers carry that too: a hacked gateway or auth Worker can copy or mint a live token and replay it at `/mcp` and `/api/*`, reading that user's data, for any user with an approved remote client, while that token works.
- **A native app's window shows only what the release key signed.** The web client it runs is the copy built into it or a bundle the release key signed (`src/web/bundle.rs`), which it checks before keeping it and again every time it starts: signature, shell version, and never older than what it has. The Workers and the bucket only carry bundles (at `<address>/updates/`), so a hacked Worker can't change what an app runs, where it could in a browser. The window loads the bundle from the app's own origin, never a remote one, so it can ask the app for exactly what the built-in copy can. A bad signature, a failed download or a bundle whose page doesn't start leaves the app on its last good bundle or the built-in one, which stays as the floor; a new one goes in when the window next opens, never under a running page.
- **A phone app's window runs the same client as a browser**, from its bundle (the client's Rust, as WebAssembly, in the page): a change to it, a `READS` bump included, reaches the app at its next open with no native build. Its device key stays in the OS's secret store, and signing and opening go through the app (the `Opens` and `Signs` traits' JS callbacks), which never hands the key over. An older Android System WebView has no Ed25519 in WebCrypto, so that page uses the shell's own client instead, as a shell built with no WebAssembly does. What runs with no window (widgets, notifications) stays the shell's Rust; a shell behind `READS` keeps showing the last widgets and the window says to update, and needs a native build, as a change to what the shell gives the page (`web::SHELL`) does.
- **A computer's window is a view of its onet** (Mac, Windows, Linux; Andre, 11-10), carrying no key and no background program: the page asks through the app, which asks the computer's onet on its loopback as the CLI does (`client/native/src/here.rs`), and so do the widgets and a Windows push, whose note onet opens. onet keeps what its screens' calls that only read last answered, for a window opened again to show at once, and renews its user's app schedules of an app as any of the computer's programs calls it. Signing in there names the computer's key, and onet asks to be let in with it, then reads where the network keeps its data from who's who. The first time the window opens on a computer with no `one`, it sets it up from the network's signed record (`one::latest`, the same a device updates by): on Linux in `~/.local/bin`, its `oned` a unit of the user's own systemd, with no root; on Windows by `install.ps1`, a task of theirs; a Mac's app still carries its `oned`, as its launch agent. The window's Update is `one update` (Settings › Devices, or the box that says the device needs updating), never an updater of its own. A window that had its own key before this lets it leave its user's devices (`Keyring::leave`) once the computer's onet is in, and forgets it.
- **Who can do what is signed, and kept in the bucket**: the scope database's steps, in the one order the bucket gives them, each checked by every reader. A change counts by who signed it, never by the time it claims.
- **A device's app runtime** is listed by that device alone: a compute of its own key, naming the device, carrying the device's rights to run things (`ScopeDb::device_of`). What's recorded of running things (who chose the device, its Vault grants, its app schedules, its run priority) stays against the device, the device drops its own Compute only once it has one, and it goes when the device is taken out. It opens nothing of its own and signs nothing in `global`: it asks the device's key, held by the device on its loopback (`/api/holds`, with the token the device's own programs ask with: its node's or its onet's), to open what's sealed to the device (its user's epochs among them) and to write who's who (`src/node/holds.rs`). It answers only the device's own programs, with the token in its folder (`<home>/services/apps/`, beside its key), and passes their calls on to its user's other devices as the device would. A device with one is no longer "just a client" to the recovery key. Every computer has one (`oned apps --listen=<address>`), which its onet lists the first time it runs there, or as it joins or makes a network: the runtime as a compute naming the device, then the device as a client alone, and no other step; the device's key and what's sealed to it stay as they were. Besides the epochs, Vault and app schedules' keys and its steps in `global`, the runtime asks its device's key to sign the device's requests to the relay and auth (letting in a device or a service), never a step. A pairing code it makes names the runtime, which answers the computer joining with it, so the runtime tells the relay of it with its own key: the relay lets that computer reach only the key that told it of the code.
- **Clients take who's who from the signed steps themselves**, from the freeze the network's recovery key signed, never from what a node or the relay says, and seal or hand keys only to whom they list.
- **Signing in only lets you ask.** It never opens a key, and never lets anyone in by itself. Someone already in the network says yes, at the time or in advance with an invite. A user has any number of linked identities, a passkey or an account at an OIDC provider the network has registered with (Google is one like any other), and one more is only ever linked from a device already signed in, which checks it and records it in the signed steps once its user taps to say so.
- **Who says yes.** A user's next device: one of their own, with the same short code on both screens. Someone not invited, at the network's domain, as the provider's signed token says: an admin, the same way, whose approval is the signed step listing them, so only admins add users; anyone else is refused at sign-in, before an admin is bothered. Someone invited by email: the invite, a signed step, is the approval, so they sign in with that email and go straight in. Someone sent an invite link: the link is the approval, its secret checked by the admin's device that made it, which lets them in with no tap unless their sign-in was finished from another link. Someone with no device left: an admin, once they've taken the lost ones out; what restores their own scope is a holder of the recovery key's, opening their own copy on their own device to seal it to the new one, by the code on its screen (`one devices restore`). A computer with no browser or no working sign-in: a QR, or a one-time link or code from a device already in, single use and short-lived. Every device of theirs then shows it joined, with Remove. Requests go out as ordinary pushes and stay until answered or expired.
- **Whoever answers checks the sign-in itself** (`src/onboarding/sign_in_proof.rs`), an OIDC provider's ID token for the network's own client or a passkey's assertion, each naming the new device and the network, so a hacked auth Worker can make requests and never approve one. A passkey's public key comes from auth, which keeps it, so it never counts as proof by itself. A user's next device whose sign-in can't show an ID token on record (a passkey, none it could check, or one not on record), and someone with no device left, are checked by the whole 16-letter code, as a short code alone can be matched by grinding keys offline. Auth reads a request's sign-in out only to an admin's device or that user's own. A "Not Me" is a step that takes the device's key out before it's ever listed, against that user only, and a browser refuses to seal anything to a key its own copy of who's who has taken out.
- **The recovery key's holders.** Whoever holds it can read everything and restore anyone, so an admin names them, in the network's settings, anyone in the network can see who they are, and everyone joining is told: "The owner of this network can see everything in it." Naming someone hands them nothing, and a network starts with no holder. Whoever has the key's file seals it on their own computer, once for each device, and a node keeps only what's sealed. It goes only to a holder's own device that is just a client, with no app runtime of its own, and has said what it is: never a node, which holds no keys; a browser, whose code a Worker serves; a remote MCP client; or a passkey, which is wherever it syncs. A device's `platform` is only what it says of itself, and a hacked Worker can relabel a browser as a phone, and a hacked node can list a key of its own, so what really decides is its whole code, 16 characters of a hash of its key and seal key: whoever has the key's file computes it from the very key and seal key they're about to use, and seals only if it's what a person read from that device's own screen. Each copy is signed by the recovery key and counts only if that checks, so nothing anyone else put at its name can pose as it or block the real one. Taking someone off the list stops new seals to them, and can't take back what they already have: only replacing the recovery key does (`one devices recovery-key replace`), so that's how a holder's stolen device is undone. Whoever has the key's file names a new key; every epoch and Vault key the old one opens is sealed to the new one too, under its own name; each scope still in use gets a new epoch and Vault keys sealed to the new key and not the old, so what the old one opens stops growing; and copies held under the old key stop counting. Nothing already sealed is deleted. The recovery key signs those new epochs itself, as it must for a user with no device left: besides that it only lets a device of someone already in, each an entry in the log.
- **An invite is checked by every reader.** A newcomer's device can't write who's who itself, since it holds no key to `global`'s sealed steps, so any device of the network that's online writes it for them, with no tap (Andre, 11-11: no device has to stay on for someone to join): a `device` step carrying the provider's signed token and the key that signed it, saved with the proof, as providers change their keys. Every reader checks it against the invite: only that user, for that email, that device, as the role it says, once. The invite is the approval, so whoever carries it decides nothing, but whoever carries it also says which key signed the token, and a member's device could make up both: so the admin's device that invites saves the provider's keys then in the invite, and a member's device carries it in only by one of those. Any other is carried in only by an admin's, which fetched it from the provider. Invites last days and providers publish a key before they sign with it, so that's rare. Whoever carries it in seals them what it holds of what they may open.
- **Link phishing** (Andre, 11-05): someone could start a sign-in on their own machine (any client they register, with a device of theirs named in it), send the user its link, and a provider pick or passkey tap would sign in their device. Auth tells by where a sign-in comes back to, which phishing can't change (a client's redirects can't be changed once it's registered, and only loopback or the app's own `<cli>://signed-in/` count as on the device): one finished from a link is marked, never goes straight in by an invite, and waits for a tap on a card naming the device and where it asked from. The short code doesn't cover this, as someone mid-phish has no second screen to compare it with. A tampered auth could mislabel one, and could get a user to sign in for its own device, as the browsers' code it serves could already take what a browser opens: that's the Cloudflare account's trust, and "joined · Remove" is what shows it.
- Whoever controls a user's provider account or passkey can sign in and ask. Their 2-step verification matters, and a network whose users are all at one domain has someone to say no. Letting a device in with none of the network's devices online, by a Worker that holds keys or a secret kept with the provider, was declined (Andre, 11-05): approval stays with clients.
- **One network, forever.** A key belongs to one network; networks never talk to each other.
- **An outside program acts as its user, with nothing barred** (Andre, 11-10): Claude.ai, ChatGPT or anything else that logs in through the same sign-in is a device of theirs, one per program, listed and removable, and can do what its user's other devices can, approving devices included. Devices shows "Let in by <program>" for one it approved (a label the relay's list gives, which at worst misnames), and removing a program offers to remove what it let in. There are no API tokens: it reaches the API at `<address>/api/*` (`/api/auth/` stays auth's) or MCP at `<address>/mcp` with the tokens it signed in with, as a client in the remote MCP Worker. Removing it ends its sign-in: auth stops its tokens, its object deletes what's sealed for it and everything it kept, and a sign-in it made since, for the device that replaced that one, goes on. MCP's translation runs where a node answers `/mcp`, with only what each request hands it.
- **Agents act as their user** (Andre, 11-10): on a device or in the cloud, through the CLI, MCP or the API, an agent has exactly its user's access, Shell and Computer Use included. There are no grants, sessions or per-agent permissions, and none are planned.
- **`confirm` is the agent's judgement, not a lock** (Andre, 11-10): a tool that sends or can't be undone says so, and an agent gives `confirm: true` only once its user agreed to that action. Nothing enforces it, on purpose: agents are intelligent, read it as needing permission, and ask, as a person would. The check on a client only reminds an agent that forgot.
- **Secrets stay put:** a Vault item's secret leaves a node only inside a request to one of its hosts, by an app switched on for it. Nothing reads one back.
- **Every client lists and may use the same tools.** What one may do is decided by its user's rules in the scope database and by what its keys open, never by which kind of client asks. A node signs a change to who can do what only as its own user's device, for its own programs; every other client signs its own.
- **Keys decide access; the relay decides who's on the network.** It admits only the network's endpoints, a list devices change by signed tells. The list is in a Durable Object of its own, apart from the one carrying every socket's packets (Andre, 11-11), so a relay busy or stalled with packets stops no sign-in, URL, push or telemetry asking who's on it; auth and the URL signer still ask it every time, with nothing cached (Andre, 11-11).
- **Online is a socket open at the relay** (Andre, 11-11), however quiet it's been: the relay doesn't judge whether a device said something lately. **Last seen** is when the relay last had its socket open or close, or a Worker last asked it about the device (at most every 5 minutes), a session's as the device that vouched for it. The relay's computes say both.
- **A call tries devices, and moves on fast** (Andre, 11-11): this device first, then those online, then the most recently seen, each in run priority's order; one that didn't answer lately goes after the rest until its socket opens again. An app's call that a device hasn't started within its usual time to start one (learned per device, as a host's first byte is in `src/hedge.rs`) is asked of the next too, and runs where it starts first: one that writes takes its lease before it says it started, so it runs once. A service's function has no lease, so it goes to the next only once a device can't be reached. A guard (erasing a device) tries the device, and says it's off only if it can't be reached.
- **A push is sealed to the one device it's for.** The push Worker, and Apple's, Google's, Microsoft's and browsers' push services, carry locked bytes and read none of them: they see only that a device got a push, and when. A note says which of the network's devices sent it, and an action in one is checked by the device that gets it.
- **A service runs only the build its app's latest deploy names** for its platform, by hash, the deploy signed by whoever deployed it; or, for a built-in app's whose deploy names none, the newest release. The release key signs only what we ship (oned, the node, built-in apps' services), never a network's own code.
- **Nothing updates by itself** (Andre, 11-10). Publishing a version makes it available. Devices tell the network what they're on (each onet, in `POST /relay/computes`), and every client shows each device's version with Update and Update All, pressed by a person or an agent; there's no automatic switch, and a device that's behind says so on itself. Update, from any client (Settings › Devices, Update All going one at a time, or `devices_update`), is a signed ask carried blind by the relay, whose receiver checks who signed it and that they may remove this device, then starts `one update` (`src/update`) and does nothing else. `one update` reads a signed record at the network's address (`src/latest.rs`, `<address>/updates/newest`): a GET, nothing else of the network working, no onet, app runtime or other background program, verified against the release key built in, never going backwards. A bad or missing record means staying on what it has and saying why, so no change can cut a device off from its own update. It needs the record, and the network's address, which the app runtime keeps in the home for it; it then has oned exit, for its supervisor to start it again on the new build, onet and the runtime with it. For those few seconds what asks them on the computer (its window, the CLI, onet asking its runtime) waits for them, asks again what only reads, and says a write it had sent failed, never sending it again (`src/loopback.rs`); the runtime closes its endpoint as it stops, so other devices connect to the new one at once. On a Mac it takes the app the record names (`app/<target>`, which a Mac's scheduled agent builds and publishes) and installs it whole, apart from the oned it stops. Cloudflare is in the same list, as one row: a deploy tells the relay what the Workers are on and the device they were last deployed from (`Newest::deployed`), and an admin's Update there leaves a signed ask for that device, whose receiver only starts `cloudflare deploy`, which sends what `Newest::read` picks. A deploy has each Worker's Durable Objects take the new code at once (`code_update_strategy: immediate`): Cloudflare's default lets a running one keep the old for up to five minutes. The body of `POST /relay/computes` and the signed asks are frozen with the signed record in `tests/contracts.rs`. Pre-production there's no compatibility code: a device left behind breaks until it's updated, and says so on itself. Only the signed record and the way of updating stay stable across versions.
- **A service's program runs in its sandbox** (`src/services/sandbox.rs`): no keys, the network only to the hosts its app declares, and, unless its app declares it runs as the user (said wherever it's switched on), its own OS user and folder and none of theirs; so the sandbox protects a node, not who wrote the code. A machine that can't give one runs it without, and says so on it.
- **A service is reached only through its device's app runtime** (Andre, 11-11): it binds no endpoint and isn't on the relay, so a computer is one socket there however many services it runs. A node asks a service signed by its own key and sealed to the service's seal key (`src/services/carried.rs`); the runtime passes the bytes on unread, and the service checks the signature, that the ask is fresh and taken once, and that its signer may call it as the user it names, from who's who it reads from the runtime and checks from the first freeze itself, then seals its answer to the asker. So a hacked runtime can drop or delay an ask, and learns when and how big, but can't forge, replay or read one, nor make up an answer, as when each service was an endpoint of its own.
- **Only the URL signer holds the bucket's credentials;** everything in the bucket is sealed, so what it hands out opens nothing.

## The three rules

Who can do what is the signed steps of each scope's database, in the one order the bucket gives them, and every reader checks each step by three rules:

1. the network's first step, and the recovery key it names;
2. epochs never go down;
3. each step's signer holds the permission its change needs (`src/permissions/`).

A removed device's later steps fail rule 3, because they come after its removal in the one order.

## Insights

Recorded by the network itself, in OpenTelemetry's data model and names, with no SDK or Collector (`src/insights.rs`). It's in Cloudflare Basin, not the sealed databases (Andre, 11-10), through the telemetry Worker (`cloudflare/telemetry/`): telemetry may be lost, and reading it needs no keys.

- **The path is checked by what goes down it** (Andre, 11-10). Every node, every 15 minutes, sends a span, a log and a metric named `telemetry.canary` and reads the last ones back through the same read. Two checks failing in a row is a problem for the network's admins: on Insights itself, as a badge and a problem box, and first in `one insights`. Telemetry may be lost, so one isn't.
- **Three tables that can't change.** A Basin stream's schema and a sink's table are fixed once made, so spans, logs and metrics have few fixed columns and everything else in a JSON `attrs` string. A new column means a new stream, sink, pipeline and table.
- **Every device sends its own.** Each keeps one batch and sends it about once a minute and on a clean stop; failing to is dropped. Every server span goes, since rates are read from them; steps, as real child spans, and client hops only for failures, slow calls and one trace in 20.
- **Each device names itself.** The Worker takes only rows that fit their table, and holds `service.instance.id` to the signer unless it's a node, which also writes what its clients report. A row is read with its device's name, and what's part of a device (a service, a native app's sign-in) by that device's.
- **Every client reports like a node** (Andre, 11-10). Each request a client makes (a screen's, the CLI's, an MCP server's) starts its trace and is its client span, the parent of what the nodes did of it (W3C's `traceparent`): named by its app's tool, or else by its route, saying which node answered and how it ended, and never anything a screen or call said. Kept as a node keeps a hop: failures, slow calls and one trace in 20, so a phone's battery and the bucket aren't spent on what went well. A client sends them in batches to a node it reaches (`/api/insights/report`), and keeps what no node took until one does, for up to a day. One that reached no node says why (`unreachable`, `timeout`, `lost`) and is in the Errors list itself, as no node's span is there to find it by.
- **Reading is filtered on the node.** The `insights` tool asks the Worker for the services its caller may see (an app's only if they may deploy it; the network's own program's only if they're an admin). Any device in the network may ask, so this is what a client sees, not a wall against a hacked device. The Worker runs a small fixed set of queries, its only values numbers and plain names, and never SQL from a caller.
- **Where Workers run on one machine** there's no Basin, so a stand-in answers what the Worker asks of it from SQLite (`cloudflare/telemetry/stand-in.js`), which is the one place that differs.
- **A trace is found, never scrolled to** (11-10). A list of traces asks the store for the newest with a span of what its reader filters for (service, operation, status, how long it took), over the whole range, and reads each whole: what's most common never crowds out what's looked for.
- **Nothing deletes old telemetry yet.** Basin has no retention of its own: deleting rows takes an Iceberg engine outside a Worker. So every read is bounded by Basin's own day partition, `__ingest_ts`, the only thing that prunes files: a day's read costs a day however big the table gets.
- **Errors follow OTEL** (Andre, 11-10), so what isn't an error never poisons Insights. A caller's mistake (refused, a code `insights::REFUSALS` lists) has its span status left unset and no `error.type`, its code kept in `one.code`, and is in no rate and not in the Errors list. Only what broke has status Error and an `error.type`, and anything with no code broke, a route's failure as a call's, unless the route says what it was asked isn't something it takes (`api::Invalid`, kept as `invalid`). A call no device ran says how the last one asked didn't: `unreachable`, `timeout`, `lost`, or `unavailable` when each said to ask another. A device being off is an error, since the call wasn't done, and its type says it isn't the app's. A hop keeps its own client span status and never counts against a call that went on elsewhere, and trying the devices fails only if none ran it: rates and the Errors list read server spans. A step is a child of the one call that took it. A service's functions are listed nowhere, so one called by itself is `_function`.
- **A failure names its trace** (Andre, 11-10). Every request is a trace, and whatever fails tells its caller the id: as `trace-id <id>` on the CLI and MCP, so `insights --trace-id` finds it at once. A request to the API that fails with no call running keeps one server span of its route, so the id always finds something. A row takes a minute or two to be readable, so a device keeps the spans it sent for three minutes and adds its own to a trace it's asked for: a failure's trace reads at once where it was recorded, and says the rest is on its way. A refusal at the door, before a request reaches a route, has nothing to trace and no id.
- **The Workers' own traces come here too** (11-10), from Cloudflare's OTLP export to the telemetry Worker, as `worker.<name>` services only an admin reads, each clamped as a program's OTLP is. They're tail-sampled, as OTEL's collector would: a trace is kept whole if it failed or was slow, or is one in 20 of the requests, and an event that isn't a request (a WebSocket message, an RPC) only if it failed or was slow. Every request is counted first, kept or not, as OTEL's span metrics (`traces.span.metrics.duration`), and rates read those counts; a WebSocket message or an RPC isn't a request, and isn't counted: a span sampled where it was recorded says so (`one.sampled`, how many it stands for) and is never counted itself. An RPC is named for what it called (`Relay.allowed`), and a failure that threw nothing has Cloudflare's word for how it ended as its type (`exceededMemory`, `exceededCpu`, `canceled`). A Worker's exception keeps its type, its first frame and its plain words alone (anything else is `<value>`), so Cloudflare's own explanation ("internal error; reference = <value>") is in the Errors list; it never passes through a node, so this is its cleaner. Every Worker's but two (Andre, 11-10): the remote MCP server's too, whose spans carry what any Worker's do and nothing it opened; not the Cloudflare node's, which reports its calls as every node does; and not the telemetry Worker's own. Their logs come the same way (Andre, 11-10), as `logs` rows linked to their trace and span, and only what broke: a line at error level or an exception, kept by an allow-list as OTEL's `exception.type`, `exception.message` (its first line, cleaned as an exception's is) and `exception.stacktrace` (its first frame); nothing else Cloudflare sends is read (a request's URL and headers, the caller's address, `cf`), and the Worker's cleaner hides at least what the node's does, as tests/contracts.rs holds it. An export can never make the next: it goes to the telemetry Worker's own workers.dev address, never through the gateway, and the telemetry Worker's own traces and logs aren't exported. A deploy points a destination for each there by API, which needs its token to have Workers Observability Write, and says so until it does. An export may come gzipped, or to its signal's own path under the one it was given. An export whose rows are all dropped leaves nothing to show it came, so the telemetry Worker says what one held at most every 15 minutes, as a log named `telemetry.export`: how many spans and log records and how many kept, that it couldn't be read, or that it came without its token.
- **What the network uses of Cloudflare is metrics like any other** (Andre, 11-10): one store, one way to read it, and its history beside the builds. Every hour the telemetry Worker asks Cloudflare's analytics one query for the hour before, of the network's own Workers, buckets, Durable Object namespaces, pipelines and catalog (which a deploy lists), grouped by those, the hour and the kind of operation that's billed, never by anything about a request, so there's none to leave out. It's recorded as the service `cloudflare`, an admin's to read, each product and resource in `attrs`: usage, never dollars. What it costs is worked out when it's read, from the one price table (`src/insights/cost.rs`), and `insights` says it, as an estimate. Its token reads the account's analytics and nothing else, made by the first deploy whose token may make it; until then the Workers deploy without it, and say so. A new product is one entry of `PRODUCTS` (`cloudflare/telemetry/usage.js`); a new source, another function of `SOURCES`.
- **The relay's ceiling shows before it's hit** (Andre, 11-11): every hour the telemetry Worker reads how many sockets the relay holds, by what they are, and what it refused or ended since it last asked, as `worker.relay`'s readings, an admin's to read (`insights --service worker.relay`). It isn't split until it breaks.
- **An AI call is a GenAI span** (Andre, 11-11). AI Gateway records each `ctx.ai.run` as an OTEL GenAI client span (`gen_ai.*`), a child of the call that asked, and OTEL's two GenAI metrics, token usage and duration, by operation, company, model, whose key paid (`one.paid`) and tier. Only the attributes `ai_gateway::SPAN_ATTRS` lists, each a number or a plain name: never a prompt or an answer.
- **A frame says where it was written** (11-10). A deploy keeps what maps its built `app.js` and each React screen (`dist/<name>.html.map`) to their files, and the node that recorded a failure resolves its frames with them, so what's kept is `lib/f.js:3:12`, never a place in a bundle. A map holds file names and lines, and it's still only ever a location.
- **Attributes stay in closed sets; one field is free text** (Andre, 11-10). A real failure keeps what it said as `exception.message`, from the node and from screens. Everything said passes the one cleaner on the node (`src/insights/message.rs`) before it's sent: emails, keys, tokens, URLs, IPs, phone numbers, long numbers, ids in hex and home paths become placeholders, and it's cut to a length. A refusal's is kept nowhere. Errors group by type, top frame and build; a failure the node's answer caused has only the runtime's frames, the same for every app, so its frame is what was asked (`ask:call`).

## Designed, not built

- **`onet` and `oned`** (Andre, 11-10, being built). "Node" blurred several jobs, so it goes. **`onet`** is the entry point into the network, the same on every device: its identity, who's who, connecting to the best machine, opening keys, answering the API, and the store of what it last read. It's built into the phone app, runs in a browser's shared worker, in a Cloudflare Worker for each outside program (Claude.ai, ChatGPT), and in the background on a computer, where the desktop app, the CLI and the local MCP server are views on it with no keys of their own: one key per device (built: see Trust). A phone is only ever a client, never an app server. **`oned`** only manages services, starting and stopping them and saying their versions, on computers and Cloudflare, as a user of `onet` like any other. **The app runtime is a service**, switched on per device, and does what needs something that stays on: answering other devices' calls, schedules, running apps' code, and the database copies that takes. Built so far: the API's document (`/api/openapi.json`) is made by `onet` for its own client, from the apps a node lists and what routes say of themselves (`src/says.rs`, a table that builds without the node), the same code in a browser, a computer and the Cloudflare node; and for each outside program, in `cloudflare/mcp`'s objects, `onet` serves the API at `<address>/api/*` and MCP at `<address>/mcp`. On a computer, `oned` holds no key and starts two programs, starting each again when it stops: `onet` (`<cli>t`, `onet/src/computer/`) and the app runtime (`oned apps --listen=`), on a loopback address it gives both. `onet` answers on the computer's API port and token, holding the device's key, which one lock in its home lets one process sign with, and refusing to start where its home names a network but has lost the key, which would make it a stranger. It answers what a client signs, joins a network with a pairing code or as a user signed in on the computer's window, does what the recovery key does there (the one copy the tests' nodes run too, `src/settings/recovery.rs`, writing the recovery key's own steps to the bucket itself, as no node takes them from a device), tells the relay what the device is on and hears an Update left for it, and holds the device's key for its app runtime (`/api/holds`, writing the device's steps to the bucket itself too); everything else goes to its own app runtime by its loopback, as the computer's own program, with the token in the runtime's folder (so a route only those may ask goes nowhere else), and to the rest over iroh with the keys it opens. Until the network has an address, all of that is the runtime's to answer. `oned` is a user of `onet` like the computer's other programs: it starts and stops the device's services itself (`oned::keep_parts`), asking `onet` which are on, their builds and what their apps declare (`/api/services`, which `onet` passes to its runtime), and what they're doing it tells `onet`, which says it in a hello to every app runtime of the network over what devices speak to each other (`<cli>/1`), never through the relay's own messages, which would show it services' names and what went wrong; Settings › Devices shows it with the device's runtime. Still the app runtime's: making a new network, which deploys its first apps, and a pairing code, and letting in the computer joining with it. Each keeps its own log: `<cli> logs <device>` is the runtime's, `--service onet` and `--service oned` the others'.
- **The Workers deploy from any admin's device** (Andre, 11-11): no device is their home. A real network's Workers' secrets are 1Password references, and each save of their settings keeps `settings.json` and those references (never a value) in one 1Password item, `<name> Cloudflare settings`, in the same vault. A deploy takes both from there first, so the files on a device are only a copy of 1Password's, and a device with none but a 1Password sign-in deploys as well as any.
- A user key, so a new device needs one handover and not a seal per scope: it's random, its secret sealed to each of its user's devices, and each scope's keys sealed to it beside today's seals. Nothing can hold one yet without widening what it could lose: a browser's code comes from a Worker; a phone app's window gets only what its shell hands it; a computer's onet hands its app runtime what its key opens; a remote MCP client and an app schedules machine hold only what they were approved for. It waits for a native shell that keeps one itself.
- One key per scope at a time, changed only when a user or a lost device is removed, every database copied under the new key and the old one dropped. Today a scope has numbered epochs, and a new one is made when someone loses the right to open it.
- Services each running as their own OS user per scope.
- What's left of the storage move: `docs/plan-storage-and-permissions.md`.
- Native apps keeping their own sealed copy, for reads with no network; writes while offline, replayed like a rebase, never repeating what went outside.

## Decided

Andre, 2026-11-05: the dumbest choice that works.

- Telemetry records and has no opinion (Andre, 2026-11-10). What likely needs attention is an app's call, never the pipeline's.
- Opening fast is measured, not designed (Andre, 2026-11-11). Every client says how its first screen opened (`client.open.window`, `.shown`, `.fresh`), and what those say is what's made faster. A screen shows what it last answered before its device is let in, so on a throwaway with a slow phone's latency it shows in 0.3–0.5 s and is fresh by 0.7. Write positions (a write's database and step, a read waiting on one) wait until a screen is seen showing an answer older than its own write.
- A service's identity is its own OS user on Linux (systemd's `DynamicUser=`), Seatbelt as the user on a Mac. A Windows computer runs the app runtime and no services: AppContainer can't reach its device over loopback without an exemption only an administrator can make, so its sandbox is still to design, and none is published for it.
- On Windows, `oned` is a task of its user's, started at sign-in and looked at every minute, with no administrator (`install.ps1`): it stops at sign-out, like a Mac's launch agent, because a standard user can't have a task that runs signed out. A running program can be renamed but not overwritten, so an update gives the old file one more name, then renames the new one over each of its names (`os::replace_program`).
- A service that needs the user (`user: true`: Shell, AGENTS.md, AI Usage, the Mac's Apple-data services) is allowed for any app, said plainly when adding ("Runs as you on mac"), never silently.
- The machine that deploys builds a network's own app's service, for every platform it can build; nodes never build. A network's own Mac service gets no Mac permissions.
- One node runs a service. When it's gone nothing moves by itself: the app shows one problem box with Move. For a group's or everyone's app, the admin adding it picks one of their own nodes or the Cloudflare node, and any admin may move it to one of theirs.
- No Cloudflare Containers. The Cloudflare node runs the app runtime and services built for Cloudflare (Models answers with Workers AI there); Agent Devices stays on computers. Left: a network's own app's service built for Cloudflare, until someone needs one; AI Usage doesn't show its spend. Apps reach Workers AI through AI Gateway, by Cloudflare's REST API with the network's key, from any node.
- Risks: TCC attribution on a Mac is only learned by trying; `sandbox-exec` is deprecated though Apple ships on it (the fallback is an App Sandbox entitlement per helper, which only we can sign); moving a service loses its state unless it moves it itself.
