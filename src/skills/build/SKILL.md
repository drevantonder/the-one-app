# Building an app

An app is a folder with one JavaScript module, `app.js` (or `app.ts`): its tools, which agents call; its screens and widgets, which users see; and the data it keeps. Everyone in {{yours}} can read every app's code.

1. Look first: `{{cli}} search "<words>"` may find an app that already does it. To change someone else's, fork it: `{{cli}} fork <app> <name>`.
2. Copy `example/` beside this file (`app.js` and `screens/main.jsx`, a small app with data, a screen, a widget and tools), and change it. Read an app that's close for anything else: `{{cli}} source <app> src/app.js` (`apps_code` with `path: "src/app.js"`; its files list says where each is), and in a checkout of {{name}}'s code the built-in apps are the folders in `apps/`.
3. Name it: a folder name of lowercase words joined by `-` (`water-log`), which is its name. `title` is what a person reads, `icon` a [Phosphor](https://phosphoricons.com) icon's name (`drop`), and `color` a hex colour, the tile's: leave it out and the tile is grey.
4. Its tools, for agents, which read them cold:
   - Every tool has a `title` (a few words, "Log water") and says `reads: true` or `reads: false`. What sends to a user or can't be undone also says `confirm: true`.
   - Every tool has an `output`, the same way `input` says what it takes: `{ type: "string" }`, or an object's fields, with `required` only for those it always gives. The node holds every answer to it: one that gives back what it doesn't say fails, naming the tool and the field.
   - Its description says what it does, when to use it rather than its neighbour, and what comes back, in a sentence or two. Every input says what it takes, with its format (`an ISO 8601 date-time, 2026-11-01T09:00`) and where to get it (`a message's id, from gmail search`).
   - An app wrapping another product's API gives that API's own tools, names, inputs and paging, since agents know them. It gives back what the API gives, without bulk nobody reads; its own data in plain units (ISO 8601 times, `37 GB of 250 GB`).
   - An error says what was wrong and the fix: `no event 123: ids come from calendar events`. It doesn't include the data (an email, a name, what was typed): what a real failure says is kept in Insights, cleaned. What's the caller's to change is a refusal, `throw Object.assign(new Error("…"), { code: "refused" })`, which isn't an error, and whose text is kept nowhere.
   - A slow part worth a name in Insights: `await ctx.span("score", () => work(), { rows: 3 })`. Its name is a plain word, its attributes numbers or true and false, never text.
5. Its data: a database per scope, made by `schema` (`user`, `group`, `global`, each a list of changes, oldest first: add new ones at the end, since a database keeps what it has). In a tool, `ctx.user` is the caller's own, there wherever the app is added. `ctx.global` is everyone's, and `ctx.groups` and `ctx.group(id)` a group's, which a group's members share; a screen opened on a group's page knows it from `one.scope` (`group:<id>`) and hands it to its tools. Keep a person's things in `ctx.user`, and only what's shared in a group's. `query` reads; `exec` is written when the call returns, so give rows ids you make (`crypto.randomUUID()`). `ctx.now()` is UTC: a user's "today" is the screen's or the agent's to say, as a `day` input the tool takes. Who may do what to its own things (a repo's owner and collaborators) is its `types` and `relations`, answered by `ctx.<scope>.may(verb, object)`, as Repos does.
6. A key or password is a Vault item, never in code. Declare what it needs in `vault` (`vault: { api: { title: "Weather key", type: "API key", hosts: ["api.weather.com"], fields: { weather_key: { label: "API key", secret: true } } } }`, and `{{weather_key}}` in a `fetch`'s URL (after the host), headers or body is filled in on the way out, as written and only for those hosts). Then ask the user for it with `{{cli}} vault request <app> --need api` (`vault_request`), give them the link it prints, and wait for them: `vault_status` says when it's done. An account to sign in to: see `{{server}}-accounts`.
7. Its screens, React with shadcn's components through `@one/ui`: each `screens/<name>.jsx` is built when you deploy into `dist/<name>.html`, which `app.js` imports as text and gives as that screen's `html`. Both the `deploy` tool and `{{cli}} deploy` build it, so write React even when you only have MCP. React and `@one/ui` come from the page: import them, and never put them in package.json; other npm packages go there.
   - Use shadcn's components by shadcn's names (Button, Card, Dialog, Sheet, DropdownMenu, Tabs, Input, Switch, Badge, Skeleton…) and ours: `Grid`, `List` and `ListRow`, `Split`, `Empty`, `Problem`, `Icon`, `AppIcon`. `ui/index.ts` lists them.
   - The app's own name is in the bar above the screen already: don't write it again. The screen starts with its content, at `p-5`.
   - Never a page width (`max-w-*`, `mx-auto`): `Grid` fills its room with as many columns as fit, `List` stops at a readable width, `Split` shows what a list opens beside it where there's room. Tailwind's classes and container queries (`@container`, `@md:`) work in `className`, with shadcn's theme (`text-muted-foreground`).
   - Content first; order from type size and weight, not boxes or shadows: the number that matters is big, what explains it grey and small. Few words: a title and the action. One `default` button per view, the rest `secondary`, `outline` or `ghost`; red only for `destructive`; colour only for "this needs you". Fine is silent. An empty screen is one grey line (`Empty`); a problem shows on the thing it's about (`Problem`: a title, one sentence, the action that fixes it).
   - Instant: draw everything that doesn't need data at once, and never the word Loading. Ask for what the first view needs all at once (`Promise.all`). After an action, show its result at once and send the call; put it back and say why only if it fails. On `one.on("changed", …)`, load again.
   - With no build at all (a connector to {{yours}}'s address, not `{{cli}} mcp` on their machine, can't run one): a screen's `html` can be a string with `<meta name="@one/ui">`, `<div id="root"></div>` and a `<script type="module">` that takes React and the same components from `OneUI` (`const React = OneUI.react, ui = OneUI["@one/ui"], { createRoot } = OneUI["react-dom/client"]`, then `React.createElement(ui.Button, …)`). Their own classes work; Tailwind's others don't, so use `style` for the rest.
8. A widget, when there's something worth seeing at a glance (today's count, what's next): it lands on the page by itself when the app is added. Each returns a tree of nodes, `ui/widget.tsx` the list of them, and the example has one.
9. What an agent should know without asking goes in `hooks.prompt(ctx, { since })`: shown to every agent of the user's with their prompt. It only reads, answers fast, and says nothing when there's nothing new. For what a sandbox can't do (a device's files or programs, a long connection, a local model), an app publishes a service: copy `apps/whatsapp/service/`, and declare it (`service: { network, user, platforms }`, `uses: { services: ["<app>"] }`). It builds on the deploying machine, and a device runs it once its owner switches it on (`{{cli}} services on <app> --device <device>`).
10. Deploy: `{{cli}} deploy <folder>`, or the `deploy` tool with each file's text. It says whether the app started, and fix what it says before going on.
11. Put it on a page: `{{cli}} add <app>` (the `add` tool, scope `user`) for your own, `--scope <group>` for a group's, `--scope global` (admins) for everyone's. It's on their devices at once. Without this, nobody sees it.
12. Check it: run each tool (`{{cli}} <app> <tool>`, `--trace` for where it failed) and take out your test data. You can't see a screen: say so, and ask them to open it and tell you what they see. If it says "This screen stopped working", what follows is the error: ask them for it, or look at what you last changed. `{{cli}} deploys <app>` lists its versions and `{{cli}} deploy <app> --version <hash>` (`deploy` with `version`) puts one back.
13. Tell the user, in a sentence, where it is: on their page and in the sidebar, on all their devices, and with a widget if it has one. Don't list its tools.

To change an app: edit it and deploy again. A screen that's open shows the new version the next time it's opened. To remove one, `{{cli}} remove <app>` takes it off a page, and what it kept there stays for when it is added back; `{{cli}} apps delete <app> --confirm` deletes it everywhere, into Recently Deleted, only once the user agreed.

Keep its code wherever you like (Repos, GitHub, any git host), and link it: `{{cli}} apps source <app> <link>`.

## The details

The files beside this one are {{name}}'s own code, as this build runs it: `ctx.js`, what a call's `ctx` gives an app; `one.js`, the `one` a screen gets; `ui/`, `@one/ui`'s list of what it has (`index.ts`) and its own components; and `example/`, the app to copy. Over MCP they're this skill's resources (`skill://{{server}}-build/ctx.js`), or `search` with `{{server}}-build/example/app.js`. The rest is open source: {{code}}.
