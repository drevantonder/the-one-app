# Building an app

An app is a folder with one JavaScript module, `app.js` (or `app.ts`): its tools, which agents call; its screens and widgets, which people see; and the data it keeps. Everyone in {{yours}} can read every app's code, so start from one that's close to yours.

1. Look first: `{{cli}} search "<words>"` may find an app that already does it. To change someone else's, fork it: `{{cli}} fork <app> <name>`.
2. Read the apps already built: `{{cli}} apps code <app>` (the `apps_code` tool) lists an app's files and `--path app.js` gives one. The App Store shows the same under View code, and in a checkout of {{name}}'s code the built-in apps are the folders in `apps/`.
3. Make a folder and write `app.js` (with only MCP, write it to give `deploy`). Its tools are for agents, which read them cold, so:
   - Every tool says `reads: true` or `reads: false`. What sends to a person or can't be undone also says `confirm: true`.
   - Its description says what it does, when to use it rather than its neighbour, and what comes back, in a sentence or two. Every input says what it takes, with its format (`an ISO 8601 date-time, 2026-11-01T09:00`) and where to get it (`a message's id, from gmail search`).
   - Each tool is a primitive in its truest form: an app that wraps another product's API gives that API's own tools, with its names, inputs and paging (Drive's `q`, `fields` and `pageToken`), since agents know them and combine them. A clear contract matters, not words shared across apps.
   - It gives back what the API gives, without bulk nobody reads (images, internal ids where a name will do); an app's own data in plain units (ISO 8601 times, `37 GB of 250 GB`).
   - An error says what was wrong and the fix: `no event 123: ids come from calendar events`.

   A key or password is a Vault item the person switches the app on for: never put one in code. Its data is a database per scope, made by `schema`: to change one later, make that kind's schema a list and add the change at the end, since a database keeps what it has. Who may do what to its own things (a repo's owner and collaborators) is its `types`, each with its verbs and roles, and rows of its database's `relations` saying who holds a role on what, as {{name}}'s own permissions do: `ctx.<scope>.may(verb, object)` answers it, as Repos does. Its `icon` is a [Phosphor](https://phosphoricons.com) icon's name, like `git-branch`, which every device draws filled on its tile; `Icon` draws one in a screen. What an agent should know without asking goes in `hooks.prompt(ctx, { since })`: what it gives back is shown to every agent of the person's, on each of their devices, with their prompt (`since` is null on a session's first, else when it last asked). It only reads, answers fast, and says nothing when there's nothing new.
4. Its screens: build them with React and shadcn's components through `@one/ui`. To start, copy `react/` beside this file (`app.js` and `screens/main.jsx`, the smallest app with a React screen). Each `screens/<name>.jsx` (or `.tsx`) is built when you deploy, into `dist/<name>.html`, which `app.js` imports as text (`import main from "./dist/main.html" with { type: "text" }`) and gives as that screen's `html`. React and `@one/ui` come from the page, one copy for every screen: import them, and never put them in package.json; other npm packages a screen uses go there as an app's do.
   - Use shadcn's components by shadcn's names (Button, Card, Dialog, Sheet, DropdownMenu, Tabs, Input, Switch, Badge, Skeleton…), and ours: `Grid`, `List` and `ListRow`, `Split`, `Empty`, `Problem`, `Icon` (a Phosphor icon by name) and `AppIcon`. `ui/index.ts` lists everything `@one/ui` has; `ui/*.tsx` are ours.
   - Lay out by the room each part has, never the window or a page width: `Grid` fills its room with as many columns as fit, `List` stops at a readable width, `Split` shows what a list opens beside it where there's room and in a sheet where there isn't. Tailwind's classes, with shadcn's theme (`text-muted-foreground`, `bg-card`) and container queries (`@container`, `@md:`), work in `className`.
   - The look: content first; order from type size and weight, not boxes or shadows. One `default` button per view, then `secondary`, `outline` and `ghost`; red only for `destructive`; colour only for "this needs you". Fine is silent. An empty screen is one grey line (`Empty`), with a button only for an obvious first step; a problem shows on the thing it's about (`Problem`: a title, one sentence, the action that fixes it).
   - Make it feel instant. Draw everything that doesn't need data at once, and the data as it comes (`Skeleton` only if it's slow). Ask for what the first view needs all at once (`Promise.all`), never one call after another; a call that answers in 2 ms here can take 300 ms on a phone. After an action, show its result at once and send the call; put it back and say why only if it fails. On `changed`, redraw only what changed. Fetch images and long lists as they scroll into view.

   React and `@one/ui` are recommended, not required: a screen can also be plain HTML and JavaScript, with no build: a string of HTML (its `<script>`s included) as the screen's `html`. It gets the theme (`@one/ui`'s colours as CSS variables, like `var(--muted-foreground)`, light and dark, after Tailwind's reset, so it styles its own headings, lists and buttons) and the bridge (`one.js`), but none of the components.
   For what an app can't do in its sandbox (reach a device's files or programs, hold a long connection, run a local model), it publishes a service: a program of its own in `service/` beside `app.js` (a Go module or a Rust package), declared in `app.js` (`service: { network, person, platforms }`, `uses: { services: ["<app>"] }`), which its tools call as `ctx.services.<app>.<tool>(input)`. WhatsApp's (`apps/whatsapp/service/`) is the one to copy. Deploying builds it on the deploying machine, Go for every platform and Rust for that machine's, and a device runs only the build the app's latest deploy names, once its owner switches it on (`{{cli}} services on <app> --device <device>`).
5. Deploy: `{{cli}} deploy <folder>`, or the `deploy` tool with each file's text, builds it, npm packages and React screens and all, and makes the app if it's new, owned by you. React screens are built on the machine that deploys, with its Bun (recommended) or Node: when it has neither, the deploy says so; help the person install Bun (bun.sh) and deploy again. Over a connector to {{yours}}'s address, rather than `{{cli}} mcp` on their machine, the `deploy` tool can't build them: deploy those apps with `{{cli}} deploy`. To try it out first where no one else sees it, put `throwaway` before each command (`{{cli}} throwaway deploy <folder>`): a throwaway network on this machine, with only you in it, which `{{cli}} throwaway stop` deletes.
6. Put it on a page: `{{cli}} install <app>` (the `apps_add` tool, scope `user`) for your own, `--scope <group>` for a group's, `--scope global` (admins) for everyone's.
7. Check it: `{{cli}} <app> <tool> --help`, then run each tool, and open its screens and widgets in the app on the person's Mac or phone. If something's wrong, `{{cli}} deploys <app>` lists its versions and `{{cli}} deploy <app> --version <hash>` (`deploy` with `version`) puts one back.
8. Keep its code wherever you like (Repos, `git push <your One App's address>/repos/<your handle>/<repo>.git main`, or GitHub or any git host), and link the app to it: `{{cli}} apps source <app> <link>`. Its page shows it as Source.

## The details

The files beside this one are {{name}}'s own code, as this build runs it: `ctx.js`, what a call's `ctx` gives an app; `one.js`, the `one` a screen gets; `ui/`, `@one/ui`'s list of what it has (`index.ts`) and its own components, `widget.tsx` the widget nodes as every client draws them; and `react/`, the app to copy. Over MCP they're this skill's resources (`skill://{{server}}-build/ctx.js`). The rest is open source: {{code}}. The code is the only reference, so it's never out of date.
