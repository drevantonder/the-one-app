# The One App

Your devices, and your team's, as one place for apps and agents. Read `ARCHITECTURE.md`, and `GLOSSARY.md` for what our words mean, before changing code. What machines say to each other is in the code that says it and its tests (`tests/contracts.rs` where two languages must agree): read those before changing anything that crosses a machine boundary.

## Principles

- GLOSSARY.md's words are the domain. A feature that needs a new one is designed wrong until proven otherwise.
- The core never names an app. The starter apps use exactly what anyone's app can.
- Clients, nodes, and the Workers at the network's address. Clients are devices, what people and their agents use, and the only place keys are opened; nodes run calls with the keys a caller hands them and hold none; at the network's address a few small Workers on Cloudflare, each named by its job (gateway, sign-in, relay, URL signer, push), route, sign in, relay, carry pushes and sign bucket URLs, and open nothing. A hacked node gets only the calls it ran while it was hacked; a hacked Worker reads no data, though the Workers serving browsers' code could take what browsers open, which is why they stay small. ARCHITECTURE.md's rules are the design.
- Each app's database for a scope is the truth, kept sealed in the network's bucket; who can do what is a signed log kept forever.
- Dumb beats clever. Delete before adding. No dependency without a reason written in its commit.
- One name per thing. A rename reaches everything in the same change: code, files, docs, screens, CLI and MCP text, every caller and the data, rolled out to every device together. No aliases or fallbacks for old names, and no internal words (module names, "provider") where a person reads. What a person joins and uses is a network, "your One App network": "You've joined your One App network". A workplace's custom build is shared, so it's "the" with its name: "You've joined the PTC App network". Node, oned and scope are our words, not theirs.
- The old One App and the PTC App are feature lists, not code to copy.

## Design

- Three layers. Principles, the same everywhere: content first; order from type size and weight, not boxes, outlines or shadows; colour is for app icons and for warn or danger ("this needs you"), never for "tap this": a button's weight says how much it matters; fine is silent (no "Connected" or green); a problem shows on the thing itself, as one problem box (symbol, title, one sentence, the action that fixes it); an empty screen is one grey line, with a button only for an obvious first step; one component per job.
- Our look, the same on every client: shadcn's design principles, language and component names, with its neutral theme. One `default` button per view, then `secondary`, `outline` and `ghost`; red only for `destructive`. App icons as gradient tiles, external brands' real logos, red count badges, Phosphor icons. Layout by container queries: each part sizes itself, grids fill the room, lists stop at a readable width, and what a list opens shows beside it where there's room. Never a page width. Screens are React + shadcn, through `@one/ui` (`src/screen/ui`), by choice, not by rule: a screen is HTML and JS. Every screen in this repo is on it; one that doesn't opt in gets its theme and the bridge, and native UI goes once it's moved.
- The platform's own: only what a web view can't do (passkeys, keychain, push, the scanner, files, home-screen widgets, the Mac's menu bar item). The sidebar, sheets, menus and alerts are the web's, the same everywhere.

## Work

- `one throwaway` (`target/debug/one throwaway` for your build, which `cargo test` or `cargo build` made: never build release to try it, which compiles it all again) starts your checkout's own network beside the real one, with only what every new network starts with (what a new person sees) and its own Workers, where its person signs in with no passkey. Test there with `one throwaway <command>` or `one throwaway mcp`, and its repos with `one throwaway git clone|push <its address>/repos/<owner>/<repo>.git` (plain git there is told to install the CLI); `one throwaway client web|linux|mac|iphone|android|windows` gives a client of your checkout’s build signed in to it (linux on this machine, mac on the Mac beside the person's app, iphone on a simulator of its own there, the others on a copy of a device borrowed for you), and says how to see and use it; `--as sam` (web, linux, android) gives one signed in as Sam, whom its person invited with Add Someone, for what an invited person sees and anything with two people. `one throwaway stop` deletes it and gives its devices back.
- `cargo test` before every commit, on what you'll push (after your `pull --rebase`), and `gh signoff` once it's pushed: tests run on our own machines, never in CI. A commit of only docs (`*.md`, `docs/`) needs none, nor one of only a Go service; everything else does, since the tests hold the Workers' JavaScript to the Rust. `tests/sim.rs` runs the simulator; a failing seed is a bug, never a flake.
- Tests are few, and only for what using it wouldn't show: secrets and who may do what, data kept and restored, releases, and where two languages must agree. A path you'd see work or break in `one throwaway` gets no test.
- We're pre-production: a rename or a change of shape that machines see reaches every caller in the same change, with no backwards compatibility and nothing kept for older devices, and every device updates. Stored data is migrated, never lost.
- Push to `main` as you go (pull with `--rebase` first: several threads on several machines work on it at once). From a worktree branch push `git push -u origin HEAD:main`: the `-u` is what lets a plain `gh signoff` find what you pushed. After each push, run `one update` on personal (`ssh personal` from elsewhere; linux has no Rust toolchain). It sends out only what changed since the last update there, so start it and keep working: docs and tests, nothing; built-in apps, their deploys; a Go service, built for every platform and published, which each device running it takes; the node, built (neither it nor `one release` tests: you did, before your commit), which every Linux node then takes, and the Workers on Cloudflare and the Cloudflare node, deployed by `one cloudflare deploy` from their one home, the device that first deployed them (named in `<home>/cloudflare/settings.json`, with their secrets: linux for The One App), where another device's deploy refuses and names it, and `one update` passes it over; the Mac app (and the node, which is in it), built by each Mac at once (a newer update stops the build it's on), then the iPhone app if what it's made of changed, installed on the paired iPhone whenever devicectl reaches it unlocked, with the next update saying what the iPhone has and if a build failed; and, beside it from the start, PTC's update (personal's `~/.local/share/one/after-update`). A Worker change nodes need before they take it: deploy it first, with your build (`target/debug/one cloudflare deploy` on their home). Updates there take turns, each with main's tip when its turn comes, and one whose commit an earlier one already sent out stops at once. `one release vX.Y.Z` sends out everything, waits for the Macs, and publishes it on GitHub, where the installer gets it.
  - Never poll or wait in a loop for an update or a Mac: `one status --until $(git rev-parse HEAD) [--device <name>] [--timeout 10m]` blocks until each device runs that commit (or a later build) and its services answer, says where a Mac's build failed, and exits non-zero otherwise; a second `one update` waits for the first by itself.
  - An app is quicker still with `one deploy apps/<name>` from your checkout; if it needs something new from the node, deploy it once `one update` has sent that out.
  - A service: switched on in Settings › Devices or by `one services on <name> --device <device>`, which sets it up there; an app's own in Go (`apps/<name>/service/`) is sent out by `one update` when that folder changed, and `one services try apps/<name> --device <device>` puts your checkout's build on a device at once, until a newer one is sent out.
- Before ssh, look inside what runs: `one <app> <tool> --trace` prints a call's answer, then which device ran it, each wait, where its data came from and the total (also when it failed), and `one logs <device> [--service <name>] [--since 10m] [--grep <text>]` reads a device's node or service log over the network (`one throwaway logs …` for yours); a node that began before this has none.
- Never print a secret. Check a file that holds them by its names or hashes, never its values. The Workers' secrets are read with Varlock from `<home>/cloudflare/.env.local`, as references to 1Password for one people use.
- PTC's network runs The PTC App on linux and ptc: main's code built with the `config.toml` in PTC's own repo, `the-ptc-app` in The PTC App's own Repos (`https://v2.ptcau.app/repos/andre/the-ptc-app.git`; this repo never names PTC). Its update (`ssh drevan@100.76.107.116 '. ~/.profile; PTC_HOME=~/.local/share/the-ptc-app nice ~/.local/lib/the-ptc-app/ptc update'`, its login's PATH for wasm-bindgen, in ~/.local/bin there, which `one update` runs beside its own) fetches main's tip and the-ptc-app's latest config, builds them as that custom build, signs it with The PTC App's release key, and both PTC nodes take it. On ptc the old PTC App owns `~/.local/bin/ptc` and `~/.local/share/ptc`, hence those paths. PTC has no GitHub releases: `install.sh` installs The One App.
- Apps reach devices only by a deploy: `one deploy`, or an admin adding a built-in app (the folders in `apps/`, which every release ships; see ARCHITECTURE.md; one with React screens commits their build, `dist/`, which `one deploy apps/<name>` makes). Device services, only by an owner of a device installing them there. A network's own apps (PTC's) never go in `apps/`.
- Stop what you start once you're done with it, since every thread shares these machines: `one throwaway stop`, devices you borrowed yourself (`one agent-devices give_back`), the simulators you booted (`xcrun simctl shutdown`), and your worktree (`git worktree remove`).
- One commit per change, once it works, as a Conventional Commit: `type(area): what changes, for whoever uses it`, type one of `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build` or `chore`, e.g. `fix(repos): a push shows in its list the moment it's made`. No co-author or "Generated with" lines.
- Document only what the code can't say.
- Nothing describes the code but the code: no hand-written references that can drift; generate them or point at the source.
