# The One App

Your devices, and your team's, as one place for apps and agents. Read `ARCHITECTURE.md`, and `GLOSSARY.md` for what our words mean, before changing code. What machines say to each other is in the code that says it and its tests (`tests/contracts.rs` where two languages must agree): read those before changing anything that crosses a machine boundary.

## Principles

- GLOSSARY.md's words are the domain. A feature that needs a new one is designed wrong until proven otherwise.
- The core never names an app. The starter apps use exactly what anyone's app can.
- Clients, nodes, and the Workers at the network's address. Clients are devices, what users and their agents use, and the only place keys are opened; nodes run calls with the keys a caller hands them and hold none; at the network's address a few small Workers on Cloudflare, each named by its job (gateway, auth, relay, URL signer, push), route, sign in, relay, carry pushes and sign bucket URLs, and open nothing. A hacked node gets only the calls it ran while it was hacked; a hacked Worker reads no data, though the Workers serving browsers' code could take what browsers open, which is why they stay small. Two Workers are not among them: the remote MCP server is a client, so it opens keys while an MCP client calls, and the Cloudflare node is a node like any other. ARCHITECTURE.md's rules are the design.
- Each app's database for a scope is the truth, kept sealed in the network's bucket; who can do what is a signed log kept forever.
- Dumb beats clever. Delete before adding. No dependency without a reason written in its commit.
- Code that changes together lives together; code that changes for different reasons isn't tied. A feature is one folder (its CLI command, routes, node handler and tests beside each other), not a line in every layer. Nothing hides a link: no copies of logic or values (one source, or a test in `tests/contracts.rs` where two languages must hold the same), no module reading state another sets behind its back, no call order callers just have to know. Callers see a small interface, never internals; stable code never imports what changes more often than it. No pass-through wrappers, settings for what never varies, or dead code.
- A special case is a missing design: an `if` for one value or app, a parameter for one caller, a swallowed error, a retry or a sleep, a skipped test. Fix the design so it goes; keep one only when the outside world needs it, with a comment saying what in the world.
- Comments say only what the code can't: something outside it (the proxy drops websockets, so we poll). One that restates the code, even as a why, goes.
- One name per thing. A rename reaches everything in the same change: code, files, docs, screens, CLI and MCP text, every caller and the data, rolled out to every device together. No aliases or fallbacks for old names, and no internal words (module names, "provider") where a user reads. What a user joins and uses is a network, "your One App network": "You've joined your One App network". A workplace's custom build is shared, so it's "the" with its name: "You've joined the PTC App network". Node, oned and scope are our words, not theirs.
- The old One App and the PTC App are feature lists, not code to copy.

## Design

- Three layers. Principles, the same everywhere: content first; order from type size and weight, not boxes, outlines or shadows; colour is for app icons and for warn or danger ("this needs you"), never for "tap this": a button's weight says how much it matters; fine is silent (no "Connected" or green); a problem shows on the thing itself, as one problem box (symbol, title, one sentence, the action that fixes it); an empty screen is one grey line, with a button only for an obvious first step; one component per job.
- Our look, the same on every client: shadcn's design principles, language and component names, with its neutral theme. One `default` button per view, then `secondary`, `outline` and `ghost`; red only for `destructive`. App icons as gradient tiles, external brands' real logos, red count badges, Phosphor icons. Layout by container queries: each part sizes itself, grids fill the room, lists stop at a readable width, and what a list opens shows beside it where there's room. Never a page width. Screens are React + shadcn, through `@one/ui` (`src/screen/ui`), by choice, not by rule: a screen is HTML and JS. Every screen in this repo is on it; one that doesn't opt in gets its theme and the bridge, and native UI goes once it's moved.
- The platform's own: only what a web view can't do (passkeys, keychain, push, the scanner, files, home-screen widgets, the Mac's menu bar item). The sidebar, sheets, menus and alerts are the web's, the same everywhere.

## Work

- Two programs: `one` (cli/) is what a network's users, admins and their agents have, and ships; `one-dev` (dev/) is for whoever builds this repo, its own or a custom build (updates, releases, a throwaway network), and never ships. A command only someone with a checkout needs goes in `one-dev`. `one-dev` is primitives only: what must be exact or is costly to get wrong, each saying what it takes in `--help`. When and why to run them are short skills in `dev/skills/`: ship a change (`ship`), see a UI change (`see-a-ui-change`), `release`, `ptc-update`, `look-through-screens`, `mac-behind`, `try-a-service`. Read the one you need, and use your judgement.
- `one-dev throwaway` (`target/debug/one-dev throwaway` for your build, which `cargo test` or `cargo build` made: never build release to try it, which compiles it all again) starts your checkout's own network beside the real one, with only what every new network starts with (what a new user sees) and its own Workers, where its user signs in with no passkey. Test there with `one-dev throwaway <command>` or `one-dev throwaway mcp`, and its repos with `one-dev throwaway git clone|push <its address>/repos/<owner>/<repo>.git` (plain git there is told to install the CLI); `one-dev throwaway client web|linux|mac|iphone|android|windows` gives a client of your checkout’s build signed in to it (linux on this machine, mac on the Mac beside the user's app, iphone on a simulator of its own there, the others on a copy of a device borrowed for you), and says how to see and use it; `--as sam` (web, linux, android) gives one signed in as Sam, whom its user invited with Add Someone, for what an invited user sees and anything with two users. `one-dev throwaway stop` deletes it and gives its devices back.
- Before each commit, run the tests your change could break and only those: you choose (`cargo test -- --list` lists them; `cargo test --test contracts` or `cargo test <name>` runs some) and say which in the commit's body (`Tested: contracts auth`). A change to a screen alone needs its build (`bun run build` in `src/screen/ui`), and what crosses to a Worker or the bridge also needs `tests/contracts.rs`. Run all of `cargo test` when you can't tell, or for signing, releases, the update path, keys, who may do what, and stored data. `gh signoff` once it's pushed: tests run on our own machines, never in CI. After a `pull --rebase` that follows a passing run, test again only if a commit it brought in touches a file yours does; otherwise push as it is. A commit of only docs (`*.md`, `docs/`) needs none, nor one of only an app's service written in Go. `tests/sim.rs` runs the simulator; a failing seed is a bug, never a flake.
- Tests are few, and only for what using it wouldn't show: secrets and who may do what, data kept and restored, releases, and where two languages must agree. A path you'd see work or break in `one-dev throwaway` gets no test. A test fails on a regression and only then: one that repeats the implementation, checks internals rather than behaviour, or can't fail, goes.
- We're pre-production: a rename or a change of shape that machines see reaches every caller in the same change, with no backwards compatibility and nothing kept for older devices, and every device updates. Stored data is migrated, never lost.
- Push to `main` as you go (pull with `--rebase` first: several threads on several machines work on it at once). From a worktree branch push `git push -u origin HEAD:main`: the `-u` is what lets a plain `gh signoff` find what you pushed. After each push, send it out: the `ship` skill. The signed latest record at the network's address (`src/latest.rs`, `<address>/updates/`, anyone's GET) is the one path a device updates by and must never break: every Linux node checks and takes the node itself, and each Mac's job (`client/native/mac/pull.sh`) takes the Mac app. The Workers are deployed only from their home, the device that first deployed them (named in `<home>/cloudflare/settings.json`, with their secrets: linux for The One App).
  - Never poll or wait in a loop for a device or a Mac: `one-dev status --until` blocks, and says why when it can't.
  - An app is quicker still with `one deploy apps/<name>` from your checkout; if it needs something new from the node, deploy it once the node has gone out.
  - A service: switched on in Settings › Devices or by `one services on <name> --device <device>`, which sets it up there; the `try-a-service` skill puts your checkout's build on a device at once.
- Before ssh, look inside what runs: `one <app> <tool> --trace` prints a call's answer, then which device ran it, each wait, where its data came from and the total (also when it failed), and `one logs <device> [--service <name>] [--since 10m] [--grep <text>]` reads a device's node or service log over the network (`one-dev throwaway logs …` for yours); a node that began before this has none.
- Never print a secret. Check a file that holds them by its names or hashes, never its values. The Workers' secrets are read with Varlock from `<home>/cloudflare/.env.local`, as references to 1Password for a real network.
- PTC's network runs The PTC App on linux and ptc: main's code built with the `config.toml` in PTC's own repo, `the-ptc-app` in The PTC App's own Repos (`https://v2.ptcau.app/repos/andre/the-ptc-app.git`; this repo never names PTC), sent out by the `ptc-update` skill with its own release key. On ptc the old PTC App owns `~/.local/bin/ptc` and `~/.local/share/ptc`, so The PTC App's are in `~/.local/lib/the-ptc-app` and `~/.local/share/the-ptc-app`. PTC has no GitHub releases: `install.sh` installs The One App.
- Apps reach devices only by a deploy: `one deploy`, or an admin adding a built-in app (the folders in `apps/` with an `app.js`, which every release ships; see ARCHITECTURE.md; one with React screens commits their build, `dist/`, which `one deploy apps/<name>` makes). Services, only by an owner of a device installing them there. A network's own apps (PTC's) never go in `apps/`.
- `tools/` is what agents run by hand (`iteration` reports, `agents` runs of fresh agents): `cargo test` doesn't run it and a change there sends nothing out.
- When something in building The One App slows you down or confuses you (an error that didn't say what to do, a command you had to piece together, a wait, a doc that was wrong), note one line in Agent Memory starting `Friction:`, even if you got past it. That's how it gets fixed (`tools/iteration/report.py` lists them).
- Don't write wait loops (sleep, until, pgrep, tail --pid, polling a log or a remote). Run the command in the foreground, or start it in the background and let your harness tell you when it ends. If what you need can't be waited on that way (a Mac build, a device or service coming up), note it as friction: the tool should say when it's done, not you poll it.
- Stop what you start once you're done with it, since every thread shares these machines: `one-dev throwaway stop`, devices you borrowed yourself (`one agent-devices give_back`), the simulators you booted (`xcrun simctl shutdown`), and your worktree (`git worktree remove`).
- One commit per change, once it works, as a Conventional Commit: `type(area): what changes, for whoever uses it`, type one of `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build` or `chore`, e.g. `fix(repos): a push shows in its list the moment it's made`. No co-author or "Generated with" lines.
- Document only what the code can't say.
- Nothing describes the code but the code: no hand-written references that can drift; generate them or point at the source.
