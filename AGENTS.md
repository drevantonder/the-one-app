# The One App

Your devices, and your team's, as one place for apps and agents. Read `ARCHITECTURE.md` before changing code. What machines say to each other is in the code that says it and its tests (`tests/contracts.rs` where two languages must agree): read those before changing anything that crosses a machine boundary.

## Principles

- Six primitives: key, log, view, blob, call, app. Scopes, devices, deploys, sidecars, the Vault and backups are made of them. A feature that needs a seventh is designed wrong until proven otherwise.
- The core never names an app. The starter apps use exactly what anyone's app can.
- The kernel, nodes and clients. Clients are devices, what people and their agents use, and the only place keys are opened; nodes run calls with the keys a caller hands them and hold none; the kernel is a few small Workers that route, sign in, relay and sign bucket URLs, and open nothing. A hacked node gets only the calls it ran while it was hacked; a hacked kernel reads no data, though the Workers serving browsers' code could take what browsers open, which is why they stay small. ARCHITECTURE.md's rules are the design.
- Each app's database for a scope is the truth, kept sealed in the install's bucket; who can do what is a signed log kept forever.
- Dumb beats clever. Delete before adding. No dependency without a reason written in its commit.
- One name per thing. A rename reaches everything in the same change: code, files, docs, screens, CLI and MCP text, every caller and the data, rolled out to every device together. No aliases or fallbacks for old names, and no internal words (module names, "provider") where a person reads. What a person joins and uses is "your One App": "You've joined your One App". A workplace's white label is shared, so it's "the" with its name: "You've joined the PTC App". Kernel, node, install, scope and sidecar are our words, not theirs.
- The old One App and the PTC App are feature lists, not code to copy.

## Design

- Three layers. Principles, the same everywhere: content first; order from type size and weight, not boxes, outlines or shadows; colour has two jobs, the tint for "tap this" and warn or danger for "this needs you"; fine is silent (no "Connected" or green); a problem shows on the thing itself, as one problem box (symbol, title, one sentence, the action that fixes it); an empty screen is one grey line, with a button only for an obvious first step; one component per job.
- Our look, the same on every client: plain neutrals, soft rounded cards with rows inside, app icons as gradient tiles, external brands' real logos, red count badges. Its values are `src/screen/kit.css`'s, the one list every client copies.
- The platform's own: the tint (each client passes its system tint as `--tint`), font, menus, sheets, alerts, Back and window material.

## Work

- `one try` (`target/debug/one try` for your build, which `cargo test` or `cargo build` made: never build release to try it, which compiles it all again) starts your checkout's own install beside the real one, with only what every new install starts with (what a new person sees) and its own kernel, where its person signs in with no passkey. Test there with `one try <command>` or `one try mcp`; `one try client web|android|windows` gives a client of your checkout's build signed in to it (on a copy of a device borrowed for you), and says how to see and use it; `--as sam` (web, android) gives one signed in as Sam, whom its person invited with Add Someone, for what an invited person sees and anything with two people. `one try stop` deletes it and gives its devices back.
- `cargo test` before every commit, on what you'll push (after your `pull --rebase`), and `gh signoff` once it's pushed: tests run on our own machines, never in CI. A commit of only docs (`*.md`, `docs/`) needs none, nor one of only a Go sidecar (its `go test`); everything else does, since the tests hold Swift, Kotlin and JS to the Rust. `tests/sim.rs` runs the simulator; a failing seed is a bug, never a flake.
- Tests are few, and only for what using it wouldn't show: secrets and who may do what, data kept and restored, releases, and where two languages must agree. A path you'd see work or break in `one try` gets no test.
- A change machines see must be one an older device can safely ignore (phones and Macs can run behind the devices). If it can't be, make it so first.
- Push to `main` as you go (pull with `--rebase` first: several threads on several machines work on it at once). After each push, run `one update` on personal (`ssh personal` from elsewhere; linux has no Rust toolchain). It sends out only what changed since the last update there, so start it and keep working: docs and tests, nothing; built-in apps, their deploys; the node, built (neither it nor `one release` tests: you did, before your commit), which every Linux node then takes, and the kernel and serverless node, deployed from linux, where the kernel's secrets are; the Mac app (and the node, which is in it), built by each Mac at once (a newer update stops the build it's on), then the iPhone app if what it's made of changed, installed on the paired iPhone whenever devicectl reaches it unlocked, with the next update saying what the iPhone has and if a build failed; and, beside it from the start, PTC's update (personal's `~/.local/share/one/after-update`). A kernel change nodes need before they take it: deploy it from linux first, with your build. Updates there take turns, each with main's tip when its turn comes, and one whose commit an earlier one already sent out stops at once. `one release vX.Y.Z` sends out everything, waits for the Macs, and publishes it on GitHub, where the installer gets it.
  - An app is quicker still with `one deploy apps/<name>` from your checkout; if it needs something new from the node, deploy it once `one update` has sent that out.
  - A sidecar: `sidecars/install.sh <name> <device>`.
- Never print a secret. Check a file that holds them by its names or hashes, never its values. A kernel's secrets are read with Varlock from `<home>/kernel/.env.local`, as references to 1Password for one people use.
- PTC's install runs The PTC App on linux and ptc: main's code built with the `config.toml` in PTC's own repo, PTC-AU-Tech/ptc-apps (this repo never names PTC). Its update (`ssh drevan@100.76.107.116 '. ~/.profile; PTC_HOME=~/.local/share/the-ptc-app nice ~/.local/lib/the-ptc-app/ptc update'`, its login's PATH for wasm-bindgen, in ~/.local/bin there, which `one update` runs beside its own) fetches main's tip and ptc-apps' latest config, builds them as that white label, signs it with The PTC App's release key, and both PTC nodes take it. On ptc the old PTC App owns `~/.local/bin/ptc` and `~/.local/share/ptc`, hence those paths. PTC has no GitHub releases: `install.sh` installs The One App.
- Apps reach devices only by a deploy: `one deploy`, or an admin adding a built-in app (the folders in `apps/`, which every release ships; see ARCHITECTURE.md). Device sidecars, only by an owner of a device installing them there. Install-specific apps (PTC's) never go in `apps/`.
- Stop what you start once you're done with it, since every thread shares these machines: `one try stop`, devices you borrowed yourself (`one agent-devices give_back`), the simulators you booted (`xcrun simctl shutdown`), and your worktree (`git worktree remove`).
- One commit per change, once it works, as a Conventional Commit: `type(area): what changes, for whoever uses it`, type one of `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build` or `chore`, e.g. `fix(board): a post shows the moment it's sent`. No co-author or "Generated with" lines.
- Document only what the code can't say.
- Nothing describes the code but the code: no hand-written references that can drift; generate them or point at the source.
